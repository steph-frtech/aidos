# ROADMAP — compound du besoin (track EL : Elicitation Levels)

> **Avant l'app-builder : forcer l'utilisateur à expliquer son app, niveau par niveau, au-dessus du mur ; le besoin se *compound* et suit l'architecture.**

## Intro

Ce track est un **prérequis** du roadmap app-builder (`docs/plan/ROADMAP-app-builder.md`, S53→S117). AIDOS interdit `prompt → code` (CLAUDE.md §Core rule) : l'humain possède la *vérité* (le « quoi »), l'agent possède l'*implémentation* (le « comment »), et **le mur** les sépare. Au lieu de laisser l'utilisateur jeter un prompt libre dans une boîte de texte vide, ce track le **force à expliquer son app niveau par niveau**, dans l'ordre strict de la verticale KRD §23 (`product → journey → view → control → action → operation → entity`) plus la **bande invariants** (N1, ∀) et les **quatre métadonnées par-vérité** (`truth_kind`, `verifiability`, `scope`, `authority` — S14/S15/S16).

Tout reste **AU-DESSUS DU MUR** : chaque niveau résolu sort comme **Idea** via la seule porte légale `idea-intake`. L'unique door de **capture** est `idea_capture` (provenance `human`, l'utterance verbatim, statut `draft`) ; `idea_grill`/`idea_spike` ne **capturent rien** — ils **font AVANCER** une idée existante dans le cycle `draft → grilled → spiking` (vérifié dans `back/mcp/idea-intake/main.go` : `idea_spike = advance(id, ideas.Spike)`). Il n'existe **aucun** `idea_promote_to_kernel` ; **aucune** écriture `kernel`/`mirrors`/`fitness`. Le nouveau schéma Postgres `besoin` est un schéma **distinct de la vérité**, pas une exception au mur.

L'artefact produit est l'**architecture-following requirements doc** : un **BesoinGraph** déterministe, content-adressé, dont la topologie EST la verticale KRD. Le **RedBacklog** d'Ideas qu'il émet — topo-trié selon les arêtes `constrains`/`seeds` — est l'entrée exacte que l'EPIC 4 de l'app-builder (S64 « capturez votre idée » → S65 `/grill` → S66 `/goal` → S67 behavior-macro) consomme : un besoin **déjà descendu niveau par niveau, ordonné architecturalement**, au lieu d'une intention floue.

Le besoin **se *compound*** : chaque niveau résolu devient l'**ancre figée** (pattern STRATEGY.md de Compound Engineering) que le niveau d'en dessous lit comme *grounding* et ne peut contredire silencieusement. Le compounding s'applique **en profondeur** (niveau L contraint niveau L+1, et l'espace d'options de L+1 *rétrécit mesurablement* grâce à L — via une métrique d'`OptionSpace` **déclarée et énumérable**, jamais un jugement LLM) **et dans le temps** (un second besoin similaire réutilise les ancres via le reuse-router CE05 — `DeriveCost 80` vs `ReplayCost 20`, **name-match canonicalisé**). Réutilisation **via le mur** (`firewall.ViaIdea`), jamais un apprentissage de fitness (§8, poids déclarés).

**Portée v1 (honnête, déclarée d'emblée).** Le track élicite les **7 rungs SOURCE de la verticale §23** + la **bande invariants** + la **bande policy** transversale (≥ 1 `Idea{Proposes:policy}`). Les couches kernel `saga`, `temporal`, `globalinvariant` (présentes dans `back/kernel/`) sont **délibérément hors scope v1** : un besoin multi-étapes (saga) ou un invariant temporel n'a pas encore de rung d'élicitation dédié — c'est une **OpenQuestion déclarée** pour un EL ultérieur, pas une complétude prétendue. `policy` est traitée comme **bande transversale** attachée à `operation`/`entity` (comme la bande invariants), pas comme un rung vertical séparé — décision tranchée en EL02, pas en prose implicite.

**Exécution :** `/long-run`, ids `EL00 → EL18` (**EL00** = la cible de l'app émise, ADR-only — voir EL-E0). **`EL01` est un spike de nécessité** (on prouve le besoin du track avant de construire le substrat). Chaque étape suit la boucle §6 (`/grill-with-docs` → miroir ROUGE d'abord → `/tdd` → senseurs → complétude → `/diagnose` → UI+e2e → `/improve-codebase-architecture` → accrétion d'artefacts dont son agent `step-ELnn`, ses skills/MCP, ses 2 pages Mintlify), ouvre son ticket Linear, et laisse une phase stable chaînable.

## EL-E1 — Le BesoinGraph : substrat déterministe ordonné au-dessus du mur

**Pourquoi.** Tout le track produit UN artefact que l'app-builder consomme : un requirements doc qui **SUIT L'ARCHITECTURE**. Avant tout geste d'interview ou wizard, la forme des données doit être un graphe **déterministe, content-adressé, construit par fonction pure** — parce que `determinism-first` (§6/§8) interdit que le BesoinGraph soit assemblé par un LLM, et parce que le principe de compound (chaque niveau est une ancre persistante figée que le niveau inférieur lit) exige des niveaux **ordonnés, append-only, à références résolvant par code**. Cet épic bâtit ce substrat + ses miroirs de reproductibilité + la table déclarée niveau→`Proposes` (la jointure honnête avec le closed set existant) + le config déclaré des seuils, pour que chaque épic suivant écrive DANS un graphe déjà prouvé déterministe. Il **RÉUTILISE** `records.Hash`/`Canonicalize` et le closed set `Proposes` de `back/kernel/ideas` — jamais un espace d'adresses forké.

## EL-E2 — La porte de FORÇAGE par niveau : on ne descend pas sans avoir assez déclaré

**Pourquoi.** Le cœur du track : le *forçage*. Le but de Compound Engineering — on ne planifie pas avant d'avoir *right-sized* — devient ici : **un niveau n'est pas franchissable tant qu'il n'est pas suffisamment déclaré ET tant qu'il ne contraint pas réellement le niveau d'en dessous**, et chaque niveau inférieur est contraint par le supérieur, jamais l'inverse. Cet épic construit la GATE **déterministe** par niveau (le *enough-to-proceed* **calculé, jamais déclaré** par l'utilisateur ou le LLM — anti-Goodhart §8), avec une **anti-vacuité** qui empêche le gaming (un corps parsable-mais-vide est `not_enough`), l'héritage de contrainte **mesuré sur un OptionSpace énumérable déclaré** (le compounding prouvé, pas postulé), la gate de complétude-du-besoin, le **config déclaré des seuils** (anti magic-number), et le hook `Stop` non-bypassable. Les manques vers un niveau plus profond deviennent des **OpenQuestions portées** (jamais des résiduels bloquants — exception bootstrap appliquée au besoin).

## EL-E3 — L'interview forcée + l'MCP du besoin : LLM assiste, le code juge

**Pourquoi.** Le besoin se collecte par un **BRAINSTORM forcé scopé à l'altitude courante** (pattern Compound Engineering : interrogation interactive qui *right-size* avant de descendre — discipline `/grill-me` « résous chaque branche »). Le LLM est **l'exception barricadée** (§8) : il MÈNE le dialogue d'élicitation à un seul niveau à la fois, mais le verdict `enough`, la structure du BesoinGraph, **la classification d'altitude** et la projection en Ideas sont **DÉTERMINISTES et font autorité** (le LLM défère au code, jamais l'inverse). LENS 3 demande l'élicitation comme **skills** (un geste par niveau) ET comme **MCP** (un outil par niveau, capture+validate — la porte capacité au-dessus du BesoinGraph, comme `idea-intake` l'est au-dessus des `ideas`). Tous deux **COMPOSENT** l'existant : `grill`, `classify-truth`, `view`, `action`. ADR 0009 : tout op backend exposé comme outil MCP, sans exception.

## Comment ça FEED l'app-builder

Le **BesoinGraph EST la verticale KRD §23** (un nœud par niveau, arêtes `constrains`(L→L+1) + `seeds`(L nomme un besoin plus profond)). `RedBacklog` (EL17) topo-trie les nœuds **mappants** → **l'ordre des Ideas n'est PAS arbitraire, il EST la topologie du graphe qui EST l'architecture** ; chaque Idea porte ses `anchors_above[]` (dont les nœuds `NoEmit` `journey`/`view` qui la contraignent sans émettre). Le hand-off net :

> `EmitRequirementsDoc` / `EmitIdeas` (EL16) → `idea-intake` (`idea_capture`, provenance humaine) → **app-builder S64** (« capturez votre idée ») → **S65** (`/grill`) → **S66** (`/goal`, ouverts dans l'ordre topologique du backlog) → **S67** (behavior-macro).

Au lieu d'une boîte texte-libre vide, **S64 reçoit un BesoinGraph déjà descendu niveau par niveau, ordonné architecturalement**, avec pour chaque Idea sa forme de miroir attendue (`LevelMirrorForm`) et ses ancres. ## Ce que ça change (honnête)

- **Ce que ça change vraiment.** L'app-builder cesse de partir d'un prompt plat : son entrée devient un besoin **structuré, ordonné, content-adressé, déjà trié par dépendance architecturale**, où chaque exigence mappante est déjà typée (4 métadonnées) et porte sa forme de miroir attendue. Le forçage niveau-par-niveau **anti-vacuité** attrape les contradictions ET les coquilles vides tôt (au niveau supérieur, pas au niveau code), et le compounding rend chaque app suivante moins coûteuse à élicitater (réutilisation d'ancres via le mur, sous noms canonicalisés).
- **Ce que ça NE change PAS.** Le mur est intact : ce track ne franchit **jamais** la ligne. Tout sort comme **Idea** via `idea_capture` (`HasMirror` toujours false) ; **aucune** écriture `kernel`/`mirrors`/`fitness` ; le schéma `besoin` est distinct. La promotion en vérité reste l'écriture du miroir via `/goal` — elle appartient à l'app-builder. Les poids/seuils restent **déclarés** (config `BesoinThresholds`), jamais appris (§8).
- **Limites honnêtes (déclarées, non bloquantes).** (1) **Portée v1** : seuls les 7 rungs §23 + bandes `invariant`/`policy` sont élicités ; `saga`/`temporal`/`globalinvariant` sont une OpenQuestion déclarée pour un EL futur. (2) **Réutilisation cross-app** : fiable seulement sous la normalisation `(level, normalized-intent-hash)` (EL18) ; à défaut, OpenQuestion, pas une capacité prétendue. (3) **Forward-deps** : EL19 suppose idéalement `ProjectScope` (S53), MCP-over-HTTP (S58), auth/provenance (S61/S63) ; à défaut l'MCP `besoin-intake` démarre mono-projet — OpenQuestion documentée (exception bootstrap §6). Les manques vers un niveau plus profond sont des **OpenQuestions portées**, jamais des `residual_issues` bloquants. Le coût neuf : un schéma Postgres + un MCP + un pkg Go + un hook + 2 skills + 2 routes — tout le reste compose l'existant.
- **« Done » calculé, anti-Goodhart.** Le `done` du track est CALCULÉ, jamais déclaré : tous niveaux requis `resolved` ∧ **chaque niveau rétrécit réellement l'OptionSpace inférieur** (anti-vacuité) ∧ backlog topo-trié sans cycle ∧ chaque nœud **mappant** émis comme Idea via la porte (les `NoEmit` seedent les ancres) ∧ aucun monstre (EL09). Le LLM est barricadé au seul dialogue d'interview (EL13), re-vérifié contre le schéma déterministe et la classification d'altitude par schema-mismatch — **le juge est le code, jamais le LLM qui se note**.
