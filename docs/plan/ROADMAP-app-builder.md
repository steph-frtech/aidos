## Vision — ce que nous construisons

Aujourd'hui AIDOS est un **moteur KRD complet et général en Go + Postgres** (S00–S52), un **cockpit Workbench en quasi-lecture seule** (≈ 95 % de fixtures TS statiques ; seuls `/store` et `/records` lisent le vrai Postgres), et **une seule tranche métier câblée** (le slice checkout / l'entité `Order`). Le cœur déterministe est solide et réutilisé tel quel : les DSL du Kernel, les émetteurs généralisés (`EmitGo`/`EmitTS`/`EmitDDL` sur n'importe quel `Entity` AST), le mur (hook PreToolUse + GRANTs Postgres), les miroirs/complétude, changeset/DAG/merge, goal/red-wave/semantic-diff, mémoire/pgvector, evolve/reality, les invariants S48–S52 et la couche-agent gouvernée.

**Ce qui manque, c'est tout ce qui transforme ce moteur en un produit qu'un inconnu utilise pour bâtir SA propre application.** Cette feuille de route ne reconstruit pas le moteur : elle l'**enveloppe** (multi-tenant, identité, passerelle front↔back) puis le **généralise** (modélisation multi-entités avec relations, async/jobs, blobs, autorat de miroirs piloté par écran, boucle-agent LLM exécutante en bac à sable, app émise qui démarre avec secrets/domaines/observabilité, prévisualisation/déploiement, fédération, boucle de réalité, gouvernance d'équipe, GDPR, économie/facturation, tunnel d'onboarding).

La promesse, mot pour mot du Tome — **« de l'intention au bouton »** : l'utilisateur déclare `product → journey → view → control → action → operation → policy → entity` **une seule fois** et obtient API + DB + types + UI émis, **chaque bouton prouvé par un miroir** ; rien de ce qu'il a prouvé vrai ne peut casser silencieusement ; et seule la **réalité de l'app en production** a le droit d'enseigner au Kernel une vérité nouvelle (le seul on-ramp légal, via approbation humaine). **L'humain possède la vérité ; l'agent possède l'implémentation ; le harnais tient le mur.** Cette asymétrie EST le produit.

### Disciplines KRD tenues à CHAQUE étape (non négociables)

- **Mirror-first :** un miroir rouge (Gherkin N0 / propriété ∀ N1 / fixture `state→cmd→events` N2) est écrit AVANT le code, persisté dans le schéma `mirrors`, matérialisé pour le runner. Ce rouge EST le `/goal`.
- **Le mur (défense en profondeur, DEUX couches — CLAUDE.md §2) :** toute écriture de vérité passe par `idée → miroir → /goal → approbation humaine` (propose → ChangeSet → approbation). L'agent n'a **aucun GRANT** sur `kernel`/`mirrors`/`fitness`. La passerelle HTTP et la boucle-agent ne portent **jamais** de GRANT d'écriture de vérité ; les outils above-the-line ne renvoient que `proposed`, jamais `admitted`. **L'identité et le mur ne vivent jamais dans le même point de confiance unique** : un refus côté passerelle (couche 1) DOIT être doublé d'un refus côté Postgres (couche 2 : GRANTs + RLS keyée sur l'identité propagée), pour qu'une réclamation forgée à la passerelle ne puisse toujours rien lire/écrire. Les écritures below-the-line (archive/projections) agissent directement.
- **Determinism-first :** tout ce qui peut être une fonction pure déterministe **DOIT** être du code et faire **autorité** (parsing, validation, hash, diff, routage, scoring sur poids déclarés, comptage, transformation, rendu, émission, expansion de behavior, métrage, détection de divergence, terminaison de boucle, rédaction d'Idea depuis un record). Le LLM est l'**exception barricadée**, réservée à la génération/au jugement irréductible, isolée à la plus petite surface et **vérifiée par le miroir déterministe** (le juge est le miroir, jamais le LLM qui se note lui-même). Chaque op déterministe-able porte un **miroir de reproductibilité** (même entrée → même sortie). **Jamais le LLM par convenance.**
- **Tout se fait par écran :** chaque étape user-facing ajoute une route Workbench **exécutable** (pas display-only), thémée (ADR 0010 : zinc + blue-600) et **bilingue par défaut** (ADR 0011 : `next-intl`, FR d'abord), avec un e2e Playwright qui prouve qu'un control s'exécute.
- **« Done » est calculé :** red set → vert ∧ vert antérieur intact ∧ score de mutation ≥ seuil ∧ aucun monstre. Jamais déclaré par l'agent. Tout override est une **décision enregistrée** (ChangeSet + ADR + provenance), jamais une édition.

## EPIC 1 — Fondation multi-tenant : chaque vérité appartient à un Projet

**Pourquoi (user-facing) :** un inconnu peut créer un workspace isolé pour SON app ; deux utilisateurs (ou deux apps) ne se télescopent jamais dans le truth-store singleton. C'est le prérequis de tout le reste : aujourd'hui le système est UN graphe global indivis, **zéro** colonne `project_id`/`tenant`/`owner` dans les 40+ migrations.

## EPIC 6 — Modéliser SON domaine : multi-entités, relations, async & blobs + surfaces d'autorat

**Pourquoi :** bonne nouvelle — les émetteurs sont **déjà** généraux sur tout `Entity` AST (la part déterministe difficile est faite). Mais le type map est **scalaires uniquement, ensemble CLOS, sans `ref`/relation** (cf. `back/kernel/entities/emit.go`), les entités sont écrites en testdata Go, l'Operation DSL est **synchrone request→response** (aucun async/cron/queue/outbox), et **aucun concept de blob/upload**. Une vraie app multi-entités (Order + Customer + Product) avec fichiers et travail de fond est inexprimable, et aucune UI ne modélise une entité.

| Étape | Sous-système | Objectif | Note KRD |
|---|---|---|---|
| **S71** | Kernel | **Relations dans le système de types.** Étendre l'Entity AST avec un **nœud de relation distinct** `ref` (1-1 / 1-N / N-N, sémantique FK/association/composition) + invariants d'intégrité référentielle, **en gardant l'ensemble scalaire clos** (la relation est un nœud AST, pas un scalaire). | **Miroir :** property — une relation round-trip comme AST content-adressé ; une relation vers une entité inexistante est refusée (`UNKNOWN_RELATION_TARGET`), jamais un mapping deviné (l'honnêteté de l'ensemble clos est préservée). |
| **S72** | Kernel / Generators | **Type blob/fichier + provisioning de stockage objet.** Un nouveau type d'attribut `blob`/`file` (nœud AST, ensemble clos préservé) modélisant uploads/images/documents ; un provider de stockage objet par projet (scopé `project_id`, jamais dans le truth-store, jamais dans git) ; émetteur du handling d'upload/download (URLs signées, validation MIME/taille). | **Miroir :** property — un attribut `blob` round-trip comme AST et émet un handler d'upload déterministe ; fixture — un blob du projet A est inaccessible depuis le projet B ; un upload hors-MIME/hors-taille est refusé. **ADR** du provider de stockage objet (slot `replaceable`). |
| **S73** | Kernel | **Operation asynchrone/planifiée + outbox.** Étendre l'Operation DSL avec un **nœud d'operation async/scheduled** (cron, queue, webhook-out, side-effect email/notification) et le **pattern outbox** transactionnel (écrit l'effet dans le datastore puis le dispatche, exactly-once relatif) ; sa forme fixture (`state→scheduled-cmd→events`). ## EPIC 13 — Gouverner en équipe : autorité, budgets, jardinage du Kernel

**Pourquoi :** pour de vraies équipes, « l'humain approuve » devient un AuthorityGraph scopé explicite à fitness inviolable ; KRD ne doit pas écraser l'utilisateur, donc chaque cellule déclare son budget et le Kernel est jardiné. ## EPIC 14 — Onboarding, GDPR, métrage & facturation : le vrai funnel SaaS

**Pourquoi :** `/first-app` est un tour de coach-marks simulé qui n'écrit aucune vérité ; il n'y a pas de funnel signup→premier-projet→premier-comportement→premier-déploiement, pas d'install incrémental d'AdoptionStage, **pas de droits des personnes (GDPR : export/suppression)** ni de **suppression dure de compte**, pas de facturation/métrage lié à un user/projet.
