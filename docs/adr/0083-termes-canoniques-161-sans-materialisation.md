# ADR 0083 — Statut des termes canoniques §161 sans matérialisation (Vibe Lab · KIR/KMF · Maturity ladder)

- **Statut :** accepté (décision humaine, 2026-06-15 : « GO » sur `docs/plan/PLAN-branchements.md`)
- **Date :** 2026-06-15
- **Contexte KRD :** CLAUDE.md §0 (lever l'ambiguïté du vocabulaire d'abord) · §8 (« done » calculé, anti-Goodhart) · KRD §161 (les termes canoniques du LIVRE XXX — FKE, conscience, paire-miroir, kernel effondré, **Vibe Lab**, Promotion Gate) · KRD §4 + §3931 (la porte vibe→kernel) · KRD §4600/§4794 (« Maturity : `experimental → beta → stable → critical` » + A0-A8) · ADR 0044 (FKE fondu au Tome, §161 acté ; deltas code = piste FK01-FK10 post-S117) · cf. ADR 0072 (décision-mère du plan de branchements : aucun terme du Tome ne doit flotter sans chemin ni renvoi — la même exigence d'honnêteté qui interdit un écran qui ment ou une capacité Go dormante) · réutilise `/spike` (S28), l'EvolutionSandbox (S42, `back/runtime/evolve`), `kernel.records` (S02, JSONB content-adressé), `back/kernel/autonomy` + `back/mcp/autonomy` (FK10, l'échelle A0-A8)

## Contexte

Le §0 du contrat l'exige : **lever l'ambiguïté du vocabulaire d'abord**. Or trois **termes canoniques** du LIVRE XXX, actés au §161 par l'ADR 0044, **flottent encore sans chemin ni renvoi** (preuve d'audit `wi2zxij70`) — un terme du Tome sans matérialisation ni renvoi explicite est un **monstre de vocabulaire** : on ne sait pas, en lisant le code, ce qui l'incarne.

1. **Vibe Lab.** §161 le liste comme terme canonique ; §4 + KRD §3931 décrivent la « porte vibe→kernel » (le gate d'entrée du Promotion Gate). Aujourd'hui, `grep -i "vibe.?lab|VibeLab"` sur `back/`/`front/` → **0 hit Go/TS** ; le terme n'existe que dans `docs/adr/0044`. Aucun module ne dit « ceci est le Vibe Lab ».

2. **KIR / KMF.** Le couple « Kernel Immutable Records / Kernel Mutable Facade » du LIVRE XXX (les enregistrements content-adressés vs la projection lisible). Aucun symbole portant ces sigles n'existe — mais le concept, lui, **est déjà bâti** : `back/migrations/kernel_records_baseline.sql` (S02) crée les sept tables JSONB content-adressées, append-only, `id = SHA-256(body)`, head mutable par `superseded_by`.

3. **Maturity ladder** `experimental → beta → stable → critical`. Gravée verbatim au KRD §4600 (« **Maturity : `experimental → beta → stable → critical`** ») et au §4794 (« A0-A8 + maturité »). Aucun type Go ne porte cette échelle nommée — mais l'**axe d'autonomie A0-A8** est, lui, matérialisé : `back/kernel/autonomy` + `back/mcp/autonomy` (FK10) implémentent l'enum fermé `A0..A8`, la montée par preuve, le refus `AGENT_AUTONOMY_EXCEEDED`.

L'enjeu n'est pas de tout coder maintenant (ADR 0044 a fixé : les deltas FKE arrivent par FK01-FK10 post-S117) : c'est de **trancher chaque terme** — soit il est *subsumé* par un chemin existant (renvoi explicite), soit il devient un step distinct. **Aucun terme du Tome ne doit flotter.**

## Décision

**Un seul ADR « vocabulaire orphelin » tranche les trois termes : deux sont SUBSUMÉS (renvoi explicite à un chemin vivant), un est un AXE ORTHOGONAL à matérialiser comme step distinct.**

1. **Vibe Lab ⊂ `/spike` + EvolutionSandbox — subsumé, PAS de step distinct.** Le Vibe Lab du Tome est la zone d'exploration ratchet-OFF, T0, jetable, où une intention floue devient falsifiable avant d'approcher le kernel. C'est **exactement** `/spike` (S28, `back/runtime/spike` + le `spike-confinement` hook : tout write sous `/spike` ou refusé `SPIKE_WRITE_ESCAPES_ZONE`) pour l'exploration *d'idées*, et l'**EvolutionSandbox** (S42, `back/runtime/evolve`, quarantaine MAP-Elites) pour l'exploration *de variants de cellules*. La « porte vibe→kernel » (KRD §4/§3931) est le **Promotion Gate** déjà câblé : `/spike → /harvest → idée → /goal → approbation` (jamais un write direct). **Renvoi gravé :** « Vibe Lab » = `/spike` (idées) ∪ EvolutionSandbox (variants) ; sa porte de sortie = le Promotion Gate (`/harvest` + `/goal`). Sévérité **medium** (terme structurant, mais le chemin existe). Aucun nouveau module — on documente le renvoi dans `back/runtime/CONTEXT.md` et `back/archive/CONTEXT.md`.

2. **KIR ⊂ `kernel.records` (JSONB content-adressé) ; KMF ⊂ la projection lisible — subsumé, PAS de step distinct.** Le KIR (Kernel Immutable Records) **EST** `kernel.records` (S02) : `id = SHA-256(body)`, `body JSONB`, append-only, head mutable par `superseded_by`, agent en SELECT-only (le mur §2). Le KMF (Kernel Mutable Facade) **EST** la projection lisible/régénérable de ces records (les Go structs sqlc, le DDL, les types TS de `back/gen/`, et les lentilles Workbench qui rendent le head courant). **Renvoi gravé :** KIR = `kernel.records` (les sept tables content-adressées) ; KMF = la projection lisible (gen/ + Workbench), régénérable depuis le KIR. Sévérité **low** (purement nominal — le substrat est bâti depuis S02). Aucun nouveau code ; on grave le renvoi.

3. **Maturity ladder = un AXE ORTHOGONAL à A0-A8 — à matérialiser comme delta FK10 (step distinct, post-S117).** Le KRD §4794 les liste ensemble mais distincts (« A0-A8 **+** maturité ») et le §4600 les sépare explicitement : l'**autonomie** A0-A8 répond à *« combien l'agent a-t-il le droit d'agir seul ? »* ; la **maturité** `experimental → beta → stable → critical` répond à *« quel cran de rigueur la cellule mérite-t-elle ? »* (le cliquet de §1785 : une cellule paiement en T2 et une bannière marketing en T1 dans la même app). Ce sont **deux axes orthogonaux** : une cellule `experimental` peut tolérer un agent A6, une cellule `critical` exige A2. Décision : la maturity ladder est un **enum fermé** `experimental → beta → stable → critical`, monotone (ne régresse jamais unversioned — le cliquet), **déclaré** (au-dessus de la ligne), monté **par preuve calculée** (fenêtre verte au cran courant, pas un jugement LLM — §8). Elle se matérialise comme un **delta de la piste FK10** (étend `back/kernel/autonomy` d'un second axe, ne le remplace pas), planifié post-S117 conformément à ADR 0044. Sévérité **low**. D'ici son step : OpenQuestion datée, ne bloque pas.

## Conséquences

- **Positif.** §0 honoré : aucun terme canonique du Tome ne flotte plus. Deux des trois sont **subsumés par un renvoi explicite** à un chemin déjà vivant (`/spike`+EvolutionSandbox ; `kernel.records`+projection) — zéro code, juste la levée d'ambiguïté gravée. Le troisième (la maturity ladder) est **acté comme un axe orthogonal distinct** avec son régime (enum fermé, monotone, déclaré, monté par preuve §8) et son emplacement (delta FK10 post-S117, cohérent avec ADR 0044). Anti-Goodhart respecté : la montée de maturité est *calculée* (fenêtre verte), jamais *déclarée* par l'agent.
- **Coûts assumés.** (a) Le KMF est une *projection* du KIR : il faut garantir qu'aucune lentille ni gen/ ne devient une source de vérité parallèle (le mur §2 — déjà tenu : agent SELECT-only sur `kernel.records`). (b) Distinguer maturité et autonomie demande un second enum + sa montée-par-preuve dédiée (ne pas les confondre dans un seul scalaire serait une régression de vocabulaire). (c) **OpenQuestions** (forward-deps, ne bloquent pas) : le step exact de la maturity ladder dans la piste FK01-FK10 (post-S117) ; la persistance Postgres de l'état de maturité par cellule (back-fill S17/S31) ; l'interaction maturité×autonomie dans l'Agent Factory (ADR 0085 — quel cran de rigueur impose quel plancher d'autonomie).
- Le mur, le déterminisme et l'anti-overwrite sont **inchangés** ; cet ADR ne crée (presque) aucun code — il *lève l'ambiguïté* (§0) en reliant chaque terme du Tome à son chemin, et n'ouvre qu'un seul delta futur gouverné (la maturity ladder, FK10).
