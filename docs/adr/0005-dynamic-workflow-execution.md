# The long-running exec→verify→next loop lives in a deterministic JS workflow, not an orchestrator agent

The loop that walks `PLAN.md` step by step — implement, verify, advance — lives in a **deterministic JS workflow script** (`.claude/workflows/long-run.js`), not in an orchestrator agent. **State, gating and resume live in the script**, not in any agent's context. Per step the script spawns a `step-executor` (implements one step, may write code) and a `step-verifier` (validates and corrects, holding project memory); **both return structured output** that the script reads to decide pass/fail and advance — **no report files** are written and parsed. The script advances only after a verifier pass and hands control back on unrecoverable failure, resuming from cache on the next invocation (`/long-run`). The parallel suite is the same shape: `test-suite.js` runs `TEST_PLAN.md` scenarios in parallel via `test-runner` + `suggestion-compat-checker`, gating on failures; Playwright e2e per flow runs via `playwright-tester` + the `playwright-e2e` skill. We chose this because the value of a long, gated, resumable run is **clean state and deterministic resume** — and that only exists when the loop state is reified in a script we control, not smeared across a conversation an agent cannot reliably replay.

A hard constraint follows from "resume": the workflow scripts **must avoid nondeterministic time/random APIs** — `Date.now()`, `Math.random()`, and arg-less `new Date()` are forbidden, because a re-run that reads a different clock or seed produces a different state and the cache no longer matches, breaking resume. **Timestamps and seeds are passed in via args** so a resumed run reconstructs the exact same state.

## Considered Options

- **Deterministic JS workflow script (chosen)** — `long-run.js` owns the loop: it reads `PLAN.md`, spawns `step-executor` then `step-verifier` per step, reads their **structured output**, gates, and persists step state to a resume cache. Agents are stateless workers invoked by the script; the script is the only thing that remembers where the run is. Resume is exact because all state is reified in the cache and all nondeterminism (time, random) is injected through args. Cost: this rides a **research-preview workflow surface** (the 4.8 dynamic-workflow paradigm) rather than a settled, first-class agent primitive — fewer guarantees, an API that may move under us.
- **An `orchestrator` agent driving the loop** — a long-lived agent reads the plan, calls sub-agents, decides advancement, and keeps the run state in its own context. Rejected: the loop state lives in a conversation, so **resume is unreliable** — a crashed or re-spawned orchestrator cannot deterministically rebuild "which step, which retries, what passed". It also concentrates gating logic in a model rather than in deterministic code, which contradicts §8's "the judge is deterministic". This is the surface we deliberately gave up to get clean state/resume.
- **Report files as the agent↔script interface** — executor and verifier write `.md`/`.json` reports to disk that the script parses to decide pass/fail. Rejected: it adds a brittle parse step, invites the anti-pattern of agents narrating instead of returning a verdict, and litters the tree with derived artifacts. **Structured output** from each agent is the contract instead — read directly, nothing to clean up.
- **Use `Date.now()` / `Math.random()` freely in the scripts** — simplest to write. Rejected outright: any nondeterministic read makes a re-run diverge from the cached run, so **resume silently corrupts** rather than continues. Injecting time/seed via args is the price of a resumable loop.

## Consequences

- **The orchestrator agent does not exist and must not be reintroduced.** §7 of `CLAUDE.md` already states "There is **no** `orchestrator` agent"; this ADR is its rationale. A future contributor reaching for a long-lived driving agent is reversing this decision and must say so.
- **Agents are workers with one job and a structured verdict.** `step-executor` implements one step (and may write code, within that step's own package per §6); `step-verifier` validates/corrects and carries project memory. Neither owns the loop; both answer the script. Adding a new agent to the loop means adding it as a worker the script calls, not as a new driver.
- **Resume is a first-class invariant of the scripts.** The forbidden-API rule (`Date.now`, `Math.random`, arg-less `new Date()`) is not style — it is load-bearing for resume. A lint/arch-fitness check over `.claude/workflows/*.js` should enforce it, and any new workflow script inherits the args-in time/seed convention.
- **Gating is deterministic code, not model judgement.** The script computes advance/hold/handback from structured verifier output; this keeps the "done is computed, never declared" stop condition (§8) honest at the workflow layer too. A second agent validating reduces toil, it is not the proof — the proof is the gate the script applies.
- **We accept a research-preview surface.** Because the loop rides the 4.8 dynamic-workflow paradigm, the workflow API may shift; the cost of that churn is the price for clean state and deterministic resume. If the surface stabilizes into a first-class primitive, migrating onto it is an additive change (a new `long-run.js` implementation behind the same `/long-run` entry), not a redesign.
- **The parallel suite shares the shape and the constraints.** `test-suite.js` runs `TEST_PLAN.md` in parallel via `test-runner` + `suggestion-compat-checker` and Playwright e2e via `playwright-tester` + the `playwright-e2e` skill; it obeys the same no-nondeterminism / structured-output / no-report-files rules, so reasoning about one workflow transfers to the other.
