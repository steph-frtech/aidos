# ADR 0063 — L'isolation projet × environnement : chaque couple a SA stack et SON URL, le journal de stack DÉRIVÉ du log, la page Environnement à onglets, les trois aperçus live

- **Statut :** accepté (décision humaine, 2026-06-12)
- **Date :** 2026-06-12
- **Contexte KRD :** ADR 0062 (l'instance, les workspaces et la grille — `STACK_SERVICES`/`envStackOf`, l'échelle paramétrable `BuilderState.ladder`, la spec stack-2026 gravée) · ADR 0060 (Workbench V3 — une session, des lentilles ; le transcript est la seule vérité d'écran) · ADR 0057 (le réducteur pur, la grammaire fermée — le log d'événements clos) · ADR 0006 (Doltgres = le datastore des apps émises hors prod, Postgres = la prod) · ADR 0052 (le pipeline de déploiement réel) · CLAUDE.md §2 (le mur) · §6/§8 (déterminisme-first, « done » calculé) · §9 (append-only, anti-overwrite) · la piste DP (`ROADMAP-provisioning-deploy.md` — le provisionnement réel)

## Contexte

L'addendum d'ADR 0062 avait déclaré la stack par environnement (`STACK_SERVICES`, 13 services, `%env%` substitué) — mais quatre frictions restaient, toutes remontées par l'usage réel. La stack était celle de **l'instance**, pas du **projet** : deux projets déployés en dev partageaient la même URL — l'isolation par couple projet/environnement n'existait pas. Déployer en dev ne produisait **aucun effet visible sur la stack** : pas de ticket créé puis résolu, pas de page de doc publiée, pas de point de restauration de la base, pas de trace de télémétrie — alors que c'est exactement ce qu'un vrai déploiement engendre. Le barreau d'environnement n'avait qu'une **carte** (version, date, écart) — la BDD, la télémétrie, les docs et les tickets de CE couple n'avaient nulle part où se voir. Et « voir le site en construction » n'existait pas : la conversation du lab avançait sans qu'on voie **l'app naître** — ni en web, ni en mobile, ni en desktop. Quatre mandats, une décision.

## Décision

1. **L'ISOLATION projet × environnement — chaque couple a SA stack et SON URL.** `envStackOf(env, cfg, projectSlug = "app")` (`lib/v3/instance.ts`) prend désormais le **slug du projet** en troisième paramètre ; le motif d'URL de l'app émise devient **`https://%project%-%env%.sagedesk.fr`** — `%project%` et `%env%` substitués (« ma-boutique » en dev a **SON** adresse, jamais celle d'un autre projet ni celle d'un autre barreau). Le slug injecté est le `projectId` de la session (`useV3Session` expose `projectId`/`projectName`/`instanceConfig` — ADR 0061/0062) ; sans projet, le repli `"app"` garantit qu'**aucun motif brut ne fuit** (jamais un `%` à l'écran). La fonction reste PURE & TOTALE & DÉTERMINISTE, surchargeable via les clés `stack.<service>` — l'isolation est une **donnée de résolution**, pas un fork de la table déclarée.
2. **Le JOURNAL DE STACK DÉRIVÉ — les effets de stack ne sont JAMAIS saisis, ils sont PROJETÉS du log.** Le twin pur **`lib/v3/stack-journal.ts`** : `stackJournalOf(state) → StackJournalEntry[]` (`{env, service: tickets|docs|db|telemetry, action, detail, ref}`) — une **projection pure du log du réducteur**, dans l'ordre du log, **append-only par construction** (le journal d'un état est un préfixe du journal de tout état qui le prolonge). La table de dérivation est **DÉCLARÉE** : une **capture d'idée** ⇒ une page de concept **ébauchée** (docs) ; une **promotion** ⇒ un ticket de **spec** ouvert (Plane) ; un **déploiement sur un barreau** ⇒ le ticket de déploiement **créé puis résolu** (Plane), la page de version **publiée** (Fumadocs), un **POINT DE RESTAURATION** posé sur la base — **Doltgres hors prod, le git-for-data : revenir = changer de branche** ; **Postgres + sauvegarde planifiée en prod** (ADR 0006) — et la **trace de déploiement attendue** (OTel → SigNoz). Chaque entrée porte sa **référence content-adressée** (version d'app, id d'idée, version de kernel). Le miroir (`stack-journal.test.ts`) épingle les **quatre lois** : un déploiement en dev engendre ticket créé+résolu, doc publiée, point de restauration, télémétrie ; capture ⇒ ébauche et promotion ⇒ spec ; déterminisme ∧ append-only (même état → même journal ; le journal suit le log) ; les points de restauration **s'accumulent** par env (deux déploiements dev = deux points, deux refs distinctes).
3. **La page Environnement à ONGLETS — « Ouvrir l'environnement » montre TOUT le couple.** Sur `/v3/environnements`, chaque barreau porte `v3-env-open-<env>` → le panneau `v3-env-detail` à **six onglets DÉCLARÉS et clos** (`ENV_TABS` — jamais devinés) : **Aperçu** (l'app telle que déployée LÀ — `projectionAt` × `emitApp`, les kernelVersions embarquées, le composant d'ADR 0062 réutilisé) · **BDD** (le moteur du barreau — Doltgres hors prod / Postgres en prod, l'URL résolue, les **points de restauration dérivés** `v3-env-restore-point`, le lien vers l'Historique — revenir dans le temps du projet = le rejeu) · **Télémétrie** (les traces attendues + l'URL du collecteur + le lien observabilité) · **Docs** (ébauches et pages publiées + l'URL Fumadocs du couple) · **Tickets** (créé/résolu/spec, badgés — couleurs et libellés déclarés) · **Stack** (les lignes `envStackOf` de CE projet/env — **le slug du projet dans chaque URL : l'isolation rendue visible** ; un motif vide = « non provisionné », honnête). Tout y est **DÉRIVÉ** (le journal, les URLs) — rien n'est saisi, rien n'est stocké ; la note d'honnêteté dit que le provisionnement réel par couple = **la piste DP**.
4. **Les TROIS APERÇUS LIVE — « voir le site en construction » à droite du chat.** Le lab passe en **deux colonnes** (le chat ~3fr, l'aperçu ~2fr — empilées sur mobile) : `PreviewPane` (`v3-preview`) rend **trois cadres sur la MÊME projection pure** — la fenêtre **navigateur** (trois points + la barre d'URL où s'affiche l'adresse **dev du projet**, résolue par `envStackOf`), le téléphone **Expo Go** (encoche, ratio 9:19) et la fenêtre **Electron** (feux tricolores + bande de menu). La donnée est **UNE** : `emitApp(state)` — l'émetteur déterministe d'ADR 0057 — **recalculé à chaque rendu**, donc rafraîchi à **chaque tour de chat** ; la variante ne change que la mise en forme (colonnes), jamais le contenu. La vitrine montre un onglet de navigation par route émise, une carte par entité, et les **idées capturées en indices de contenu** (verbatim, jamais reformulées, jamais inventées) ; l'app vide a son état vide amical. Les cadres mobile et desktop **disent honnêtement** (`v3-preview-expo-note`, `v3-preview-desktop-note`) que l'app Expo Go et l'app Electron **réelles** = la piste DP — trois cadres aujourd'hui, trois cibles d'émission demain, la même projection.

## Conséquences

- **Le miroir des twins : 91/91 verts** (Vitest + fast-check, `lib/v2/builder` + `lib/v3`) — les 85 d'ADR 0062 + `stack-journal.test.ts` **4** (les quatre lois du journal dérivé, ci-dessus) + `instance.test.ts` **2 de plus** (l'URL propre à chaque projet/environnement — `%project%`/`%env%` substitués, jamais un motif brut ; sans projet → le slug par défaut). **Aucun twin existant n'a été modifié** pour ce mandat — le journal est une projection NOUVELLE sur le log existant, l'isolation un paramètre AJOUTÉ avec défaut (additif, §9).
- **Le mur est inchangé (§2)** : tout est **lecture et projection** — le journal dérive du log, les URLs se résolvent, les aperçus rendent `emitApp`. Aucune écriture nulle part : pas un ticket réel, pas une page réelle, pas une branche Doltgres réelle — l'UI montre la **LOI des effets** et le dit (la note DP) ; le provisionnement l'exécutera.
- **Le déterminisme-first (§6/§8) tient sur les quatre mandats** : la table de dérivation est déclarée (un `switch` sur le jeu clos des événements), la substitution d'URL est un `replaceAll`, les onglets sont un jeu clos, l'aperçu est l'émetteur existant — **aucun LLM nulle part** ; le chat propose toujours, le réducteur juge toujours.
- **i18n** : les clés `preview*` (10) et `env*` (21) ajoutées en fr/en (`messages/{fr,en}.json`, section `v3`) + déclarées dans le layout — copie amicale, les détails techniques repliés (`<details>`), le motif WB2.
- **La pédagogie de l'isolation est rendue visible** : l'onglet Stack montre le slug du projet **dans chaque URL** — l'utilisateur voit que « ma-boutique en dev » et « ma-boutique en prod » sont **deux mondes**, et que son voisin de projet n'y vit pas. C'est la promesse « chaque couple projet/environnement a SA stack » — encaissée à l'écran avant d'être encaissée par l'infrastructure.

## OpenQuestions (exception bootstrap, §6)

- **Le provisionnement RÉEL par couple projet/environnement** — un `docker compose` (profils) **par couple**, les routes Traefik `%project%-%env%`, les bases Doltgres par env : c'est **la piste DP** (DP01–DP33, le one-shot bootstrap) — la table d'instance et le journal **déclarent** la loi, ils ne provisionnent pas.
- **Le branchement Plane/Fumadocs/SigNoz réels** — le journal dérivé devient alors un **ordre d'exécution** : chaque entrée (ticket créé/résolu, page publiée, point de restauration, trace) s'exécute contre le service réel du couple ; le journal projeté et l'état réel se comparent — un RealityMirror de la stack.
- **Expo Go réel** — servir le bundle de l'app émise + le QR code dans le cadre mobile (l'émetteur mobile est une cible d'émission à part entière).
- **Electron en VM** — empaqueter l'app émise en fenêtre desktop réelle (une VM/runner de build) ; le cadre du lab devient alors une fenêtre vivante.
