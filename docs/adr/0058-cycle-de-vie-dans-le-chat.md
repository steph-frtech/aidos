# ADR 0058 — Le cycle de vie complet dans le chat : générer, déployer test→prod (le cliquet d'environnements), voir les deltas

- **Statut :** accepté (décision humaine, 2026-06-12)
- **Date :** 2026-06-12
- **Contexte KRD :** ADR 0057 (l'IA Builder, grammaire d'intentions fermée) · ADR 0052 (pipeline de déploiement gaté des apps émises) · ADR 0056 (le graphe de connaissance du code, `diffGraphs`) · ADR 0055 (l'échelle fractale vivante) · CLAUDE.md §2 (le mur) · §6/§8 (déterminisme-first, « done » calculé) · §9 (anti-overwrite, append-only) · WB2-27 (écran `/v2/builder`)

## Contexte

L'ADR 0057 a donné au Workbench **un chat à grammaire fermée** : capturer une idée, greffer l'arbre, promouvoir, mesurer un impact, interroger l'état. Le builder savait donc **faire naître** des vérités candidates — mais pas les **vivre**. L'utilisateur veut **développer TOUTE une appli dans le chat** : générer l'application depuis ses kernels proposés, la déployer en test, la promouvoir en prod, et voir à tout moment **les deltas** entre ce qui tourne et ce qui a changé depuis. Le risque est le même qu'en 0057, déplacé d'un cran : un « déploie » magique qui exécuterait n'importe quoi dans n'importe quel ordre — la prod avant le test, une app « stockée » qui diverge de ses vérités, un delta « estimé » par un modèle. La question n'était donc pas « comment brancher un bouton deploy sur le chat » mais : **quelle forme déterministe donner au cycle de vie complet — générer → test → prod → delta ?**

## Décision

1. **TROIS intentions nouvelles dans le jeu clos** : `INTENT_KINDS = {capturer_idee, greffer, promouvoir, generer, deployer, delta, impacter, interroger}` (8, twin pur `front/web/lib/v2/builder.ts`). `generer` (« génère l'application »), `deployer` avec **environnement parsé du message** (« déploie l'application en test » / « … en prod »), `delta` (« montre le delta depuis la prod | le test »). Étendre le chat = déclarer (lexique + réduction pure + tests), exactement la conséquence annoncée par l'ADR 0057 — jamais « le modèle improvisera ».
2. **L'app est une PROJECTION PURE, jamais stockée** : `emitApp(state) → AppProjection` recalcule **toute l'app** depuis les kernels proposés — une entité par kernel (nommée du grain feuille de sa coordonnée), une route par entité, et une version **content-adressée** `app:<hash>` (le hash des versions de kernels triées : **le contenu décide, jamais l'horloge**). Même état → même app, même version ; il n'existe aucun « build » rangé quelque part qui pourrait diverger de ses vérités (déterminisme-first §6/§8 : la projection est recalculée, pas mémorisée).
3. **Les ENVIRONNEMENTS entrent dans l'état event-sourcé** : `BuilderState.envs = {test: Deployment | null, prod: Deployment | null}`, où un `Deployment` porte la version d'app déployée + les versions de kernels embarquées (la base du calcul de delta). Quatre événements nouveaux dans le jeu clos : `app_generee · deploiement_test · deploiement_prod · delta_calcule` (`deploiement_propose` est SUPPRIMÉ — remplacé par le couple test/prod, plus honnête). Le journal reste append-only (§9).
4. **LE CLIQUET D'ENVIRONNEMENTS — la loi, prouvée par le miroir** : « déploie … en test » exige ≥ 1 kernel proposé ; « déploie … en prod » est **REFUSÉ** tant que la version courante **exacte** (`envs.test.version === emitApp(state).version`) n'est pas passée en test — **test d'abord, toujours** ; et **toute nouvelle promotion ré-arme la porte** : un kernel de plus change la version d'app, la prod re-devient refusée tant que cette nouvelle version n'a pas repassé le test. Le refus est un événement explicable, pas un silence — c'est le cliquet KRD appliqué aux environnements : il ne mord que dans le bon sens.
5. **Le DELTA est un écart CALCULÉ, jamais estimé** : « montre le delta depuis la prod | le test » → `delta_calcule`, dont les impacts sont **les kernels hors de l'ensemble déployé** (différence d'ensembles sur les versions content-adressées — 0 écart juste après un déploiement, N écarts après N promotions). Sans déploiement, le delta est **total** (tout est écart), jamais une erreur. Aucun modèle n'« évalue » la dérive : le code la compte.
6. **Les boutons d'écran ENVOIENT des messages canoniques — le chat reste l'unique source de gestes** : l'écran `/v2/builder` peut offrir des raccourcis (générer, déployer en test, en prod, delta), mais chacun **compose la phrase canonique** et la repasse par le MÊME pipeline `understand`/`applyIntent`. L'écran n'a aucun pouvoir que le twin n'a pas (l'invariant d'ADR 0057, conservé tel quel).
7. **Le déploiement RÉEL reste le pipeline gaté ADR 0052** : `deploiement_test`/`deploiement_prod` sont des événements du twin pur — **aucun docker, aucun Traefik ne part d'ici**. Le vrai déploiement (l'écran `/v2/deploy`, WB2-22) reste le pipeline gaté par approbation humaine, **lié depuis l'écran** ; le chat propose et séquence, le mur tient (∀ messages : aucune écriture-vérité, aucune exécution d'infrastructure).

## Conséquences

- **Le miroir passe de 14 à 22 propriétés** (`lib/v2/builder.test.ts`, verts) : le jeu clos à 8 intentions, générer-sans-kernel refusé, la version d'app stable (même état → même app), la prod directe REFUSÉE, le chemin légal test → prod, **le cliquet qui re-mord** après une nouvelle promotion, le delta total sans déploiement, le delta 0 → 1 après une promotion — et le MUR ∀ re-prouvé sur la grammaire étendue.
- **Le cycle de vie entier d'une appli tient dans une conversation** : capturer → greffer → promouvoir → générer → déployer en test → déployer en prod → voir le delta — chaque pas un événement typé du jeu clos, chaque refus explicable, chaque version content-adressée.
- **OpenQuestions** (exception bootstrap, §6) : **brancher `deploiement_test`/`deploiement_prod` sur le pipeline réel ADR 0052** (docker/Traefik) avec approbation humaine — le chat composerait la proposition, le pipeline gaté exécuterait ; **brancher le delta sur le graphe de code ADR 0056** (`diffGraphs`) pour un écart au grain code, pas seulement au grain kernel ; **des environnements multiples déclarés** (staging, préprod…) — le jeu `{test, prod}` est clos aujourd'hui, l'étendre = déclarer, comme toujours.
