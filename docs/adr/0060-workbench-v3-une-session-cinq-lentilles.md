# ADR 0060 — Workbench V3 : une session, cinq lentilles — le chat-IA réel sous la loi du réducteur, l'history par rejeu, les parcours en graphes, le paramétrage en lecture

- **Statut :** accepté (décision humaine, 2026-06-12)
- **Date :** 2026-06-12
- **Contexte KRD :** ADR 0057 (l'IA Builder, grammaire d'intentions fermée) · ADR 0058 (le cycle de vie dans le chat) · ADR 0059 (l'échelle d'environnements, la couverture totale) · ADR 0053 (les bibliothèques d'interaction V2 — React Flow ne fait que rendre) · ADR 0054 (Fable 5, le modèle d'agent déclaré) · ADR 0056 (le graphe de connaissance du code) · WB2-25 (le registre des écrans) · CLAUDE.md §2 (le mur) · §6/§8 (déterminisme-first, « done » calculé) · §9 (anti-overwrite, append-only)

## Contexte

La V1 du Workbench, c'est **160 écrans d'experts** — un par dent du cliquet, exhaustifs, vivants, mais qui supposent le vocabulaire KRD acquis. La V2 a refondu **par concept** (WB2-00→27) : un écran par idée exécutable, jusqu'au chat à grammaire fermée de `/v2/builder` qui porte le cycle de vie entier. Restait la marche que l'utilisateur a nommée : une **V3 END-USER** — *un menu, un chat-IA central « comme GPT »* — où une personne **non technique** développe son application en conversant, sans qu'aucun jargon ne lui soit imposé, sans que l'écran ressemble à un cockpit d'ingénieur. Le danger symétrique est connu (ADR 0057) : le chat-magie, un LLM qui « comprend », décide seul et exécute. Et un danger nouveau apparaît avec les vues multiples : si le lab, l'historique, les environnements et les parcours tiennent chacun **leur** état, ils divergent — quatre vérités d'écran pour une seule session. La question : **comment donner l'expérience GPT (conversation naturelle, multi-actions, navigation totale) sans céder ni l'autorité du réducteur, ni l'unicité de l'état, ni le mur ?**

## Décision

1. **UNE SESSION event-sourcée, CINQ LENTILLES** : la V3 est un groupe de routes `/v3` avec sa propre barre latérale et un **provider de session partagé** (`app/v3/V3Session.tsx`) ; les cinq écrans — **AI Lab** (`/v3/lab`, le chat), **Parcours produit** (`/v3/parcours`), **Historique** (`/v3/history`), **Environnements** (`/v3/environnements`), **Paramétrage** (`/v3/parametrage`) — ne sont pas cinq features : ce sont **cinq lentilles posées sur le MÊME transcript**. La seule vérité d'écran est la **liste des messages** ; tout le reste (l'état, la timeline, les environnements, les graphes) est **dérivé par recalcul pur**. Il ne peut pas exister deux écrans en désaccord : ils lisent la même session via `useV3Session()`.
2. **L'HISTORY est une CONSÉQUENCE, pas une fonctionnalité** : parce que le builder est event-sourcé (ADR 0057), « revenir en arrière » n'est pas un undo codé — c'est **rejouer un préfixe**. Le twin pur `front/web/lib/v3/session.ts` le grave : `replayTo(messages, n)` = le **fold du réducteur** `applyIntent` sur les n premiers messages (l'état n'est JAMAIS stocké, il est REJOUÉ), et `turnsOf(messages)` annote le transcript entier — un `SessionTurn {index, msg, understanding, events, impacts}` par message + l'état final. Le miroir (`lib/v3/session.test.ts`) prouve : rejeu ≡ fold (∀ transcript), déterminisme, **l'état à n ne dépend jamais des messages > n** (revenir en arrière est sûr), totalité aux bornes (n clampé), et l'égalité timeline/rejeu. Brancher une autre suite = un nouveau transcript à partir d'un préfixe.
3. **Le CHAT EST UNE IA — mais LE RÉDUCTEUR RESTE LA LOI** : l'AI Lab V3 est une vraie conversation (plein écran, bulles, saisie épinglée en bas, Entrée envoie, indicateur de frappe), et le **vrai Claude** (CLI `claude --model claude-fable-5`, le précédent ADR 0054) la conduit : il répond **naturellement** ET **décompose chaque message en GESTES CANONIQUES multiples** — la palette = les phrases prouvées par le miroir du builder (les **9 intentions** d'ADR 0057/0058/0059, l'échelle entière, la navigation totale « ouvre l'écran \<nom\> »). Le contrat (`chatTurnAction`, `app/v3/actions.ts`) : prompt-palette + résumé d'état → JSON `{reply, actions[]}` strictement borné ; **chaque action proposée repasse par le MÊME pipeline `understand`/`applyIntent`** — le LLM **propose**, le code **juge** (une action invalide devient un refus doux, jamais un effet silencieux) ; **toute panne → `null`**, repli déterministe pur (fail-closed). Une bascule visible « **IA conversationnelle** » (défaut ON) donne le mode pur-déterministe — l'herméticité des e2e ET la garantie que la V3 entière fonctionne sans modèle.
4. **Les PARCOURS en graphes = une projection pure** : l'écran « Parcours produit » rend les scénarios en **graphes React Flow**, mais la DONNÉE du graphe est le twin pur `front/web/lib/v3/flow.ts` — `composesToFlow(tree, focusPath)` projette l'arbre `composes` (ou le sous-arbre d'un parcours focalisé) en nœuds **positionnés par calcul** (la profondeur gouverne X, le rang de fratrie cumulé gouverne Y — aucun aléa, aucun layout physique). Le miroir (`lib/v3/flow.test.ts`) épingle : **bijection** (un nœud de flow par nœud d'arbre, une arête par lien), déterminisme, positions **finies et distinctes**, focus de sous-arbre exact, **focus inconnu → graphe vide** (fail-closed, jamais une invention). React Flow **ne fait que rendre** — exactement la ligne ADR 0053.
5. **END-USER FRIENDLY TOTAL — la divulgation progressive** : la surface parle **français simple** (« Votre idée a été ajoutée », « Application déployée en test », « Impossible de déployer en prod : il faut d'abord passer par staging ») ; **aucun vocabulaire KRD n'est imposé** en copie primaire. Le détail technique — hashes, kinds d'événements, verdicts d'attente, coordonnées — vit TOUJOURS dans un bloc replié « **Détails techniques** » (`<details>`), ouvert par celles et ceux qui le veulent. Les états vides accueillent (« Commencez par décrire votre idée… ») au lieu d'exposer des structures. La rigueur ne baisse pas d'un cran : elle change d'étage.
6. **Le PARAMÉTRAGE expose TOUTES les données déclarées — en LECTURE** : l'écran `/v3/parametrage` rend visible tout ce qui gouverne le système et qui est **déclaré, jamais appris** (§8) : les 9 intentions et leurs lexiques, l'échelle d'environnements, les niveaux de la verticale, les facettes, les formes de miroir, les seuils. **Aucun champ d'édition** : le seul bouton est « **proposer un changement** », qui compose une phrase et l'envoie **dans le chat** — le chemin idée → miroir → `/goal` → approbation humaine, le mur intact. Modifier une donnée déclarée est une décision de vérité, jamais un réglage d'écran.
7. **V1 + V2 restent intactes** : la V3 est **additive** (`/v3`), comme la V2 le fut (§9 anti-overwrite). La barre V3 porte un lien de sortie vers le Workbench complet ; les twins V3 **composent** les twins V2 (`applyIntent`, `understand`, `initBuilderState`, `buildKernelTree`, `nodeByPath`) — jamais un fork : corriger le réducteur corrige le builder V2 ET la session V3.

## Conséquences

- **Deux twins purs + leur miroir : `lib/v3/` (12 propriétés et exemples, verts)** — `session.ts` (rejeu ≡ fold ∀ transcript ; déterminisme ; le préfixe indépendant du futur ; la totalité aux bornes ; un tour par message avec l'état final ≡ `replayTo` ; chaque tour porte son verdict et ses événements) et `flow.ts` (bijection ∀ arbre ; déterminisme ; positions finies et distinctes ; le focus exact d'un sous-arbre ; le focus inconnu fail-closed ; la profondeur gouverne X). Le mur n'a pas besoin d'un nouveau test : rejouer est un fold du réducteur, et la loi ∀ du builder (test 14, ADR 0057) couvre **chaque pas du rejeu**.
- **Le LLM gagne en surface conversationnelle, pas en autorité** : `chatTurnAction` peut proposer **plusieurs** gestes par tour (là où `reformulateAction` d'ADR 0057 en reformulait un), mais sa sortie reste du **texte re-jugé** — la surface d'autorité du modèle demeure exactement **zéro**, et le toggle garantit qu'elle peut être **débranchée** sans rien casser.
- **L'état d'écran V3 est non-divergent par construction** : une seule source (le transcript), des lentilles dérivées — le bug « deux panneaux en désaccord » devient structurellement impossible.
- **OpenQuestions** (exception bootstrap, §6) : **la persistance du transcript par projet** — la session vit aujourd'hui en mémoire d'écran ; la ranger (Postgres, par projet) donnerait des sessions reprises et partageables ; **les branches d'history nommées** — rejouer un préfixe permet déjà de bifurquer, mais les branches ne sont ni nommées ni conservées (un DAG de transcripts, le motif `dag` du noyau) ; **la palette étendue aux gestes KRD** — `/grill`, `/spike`, `/goal` comme phrases canoniques du chat, chacune exigeant son twin et son miroir avant d'entrer dans la palette.

## Addendum — le catalogue déclaré complet (2026-06-12)

La décision 6 disait « toutes les données déclarées » ; la première coupe n'en projetait que **7 sections** (les gestes du chat, l'échelle d'environnements, les niveaux, les facettes, les preuves, les seuils, les écrans). Le mandat humain a nommé le manque — *« par exemple les types d'agent avec leur harness »* — et la lentille Paramètres projette désormais **la surface déclarée ENTIÈRE de la V1 + V2**, via le twin pur **`front/web/lib/v3/params.ts`** (`paramCatalog()` → 17 sections, pur & total & déterministe ; miroir `lib/v3/params.test.ts`, **20 propriétés et exemples, verts**) :

1. **Les agents gouvernés avec leur harnais** — chaque `CoucheAgent` (`lib/agentlayer-data.ts · AGENTS` : BDD_WRITER, EXECUTOR) contribue **8 lignes** : le **modèle** déclaré (`claude-fable-5 (anthropic)`), le rôle/objectif, les **droits du mur noir sur blanc** (propose vérité, modifie miroir — et `modifie noyau : NON`, `modifie fitness : NON`, pinnés par le type même), les **zones** lecture/écriture, les **stop conditions**, les **knobs gouvernés** BA01 (température, tours max, hôtes réseau, exec, concurrence — allow-list vide = confinement max), et la **surface résolue** BA05 (outils MCP, skills, hooks obligatoires — la gouvernance ne fait que rétrécir).
2. **Les modèles connus par provider** — le jeu clos `KNOWN_MODELS_BY_PROVIDER` (pinné, jamais découvert).
3. **L'échelle d'autonomie A0–A8** — les 9 échelons (`lib/autonomy.ts · LEVELS`) + le **plafond critique A7** (`CRITICAL_CEILING` — jamais A8 sur une action critique).
4. **Les budgets du harnais (§66.3)** — les 5 caps déclarés du `HarnessCostBudget` (`CHECKOUT_BUDGET` : CI/goal, tokens LLM/goal, run de mutation, revue humaine, réduction de risque attendue) — les **caps**, jamais les rows de démo.
5. **L'échelle d'adoption (§82.5)** — T0..T4 avec `requires`/`grants` par tier + la porte unique (`THE_DOOR`).
6. **Le catalogue de behaviors (§24.6)** — `BEHAVIOR_CATALOGUE`, le jeu fermé.
7. **Les zones du mur** — `ABOVE_ZONES` (gelé — l'agent n'écrit jamais) et `BELOW_ZONES` (projection — libre), la surface déclarée du §2.
8. **Les autorités (§13.4/§13.8)** — les 7 `TRUTH_KINDS` + le graphe d'autorité verbatim (approbateurs, veto, escalade — `CHECKOUT_REGULATORY`).
9. **Les familles de liens (§17/§41)** — les 6 `LINK_KINDS`, chacune avec son mapping canonique S17 (`kindToCanon`).
10. **L'anatomie** — les 6 paires-miroir (`lib/v2/anatomy.ts · PAIR_KINDS`), dans l'ordre canonique.

Trois lois tiennent le catalogue : **(a) seuls les paramètres DÉCLARÉS entrent** (jeux clos, grammaires, caps, specs gouvernées — déclarés au-dessus de la ligne, jamais appris, §8) ; les fixtures de **démo** (RECENT_ACTIONS, ECONOMICS_ROWS, ADMISSION_ROWS…) sont des données d'exemple, **exclues**. **(b) Chaque ligne porte son module source** (`lib/…`) — la valeur est **lue** de son module déclaré, jamais recopiée : corriger la source corrige l'écran. **(c) Le mur est inchangé** : l'écran reste en **lecture seule** — le seul bouton demeure « **Proposer un changement** », qui compose une phrase et l'envoie dans le chat (`send()`) — idée → miroir → `/goal` → approbation humaine. Le miroir épingle le déterminisme (deepEqual ∀ entrée), la forme (ids uniques, lignes ≤ 200 caractères, source `lib/…`), la couverture (≥ 16 sections nommées) et chaque jeu clos par sa cardinalité déclarée (9 intentions, 3 barreaux, 7 niveaux, 8 facettes, 8 lignes × agent, A0..A8 + plafond, 5 caps, T0..T4 + porte, 7 sortes de vérité, 6 liens, 6 paires).

## Addendum 2 — projet nu, couverture totale prouvée, VS Code live (2026-06-12)

Trois retours du même jour — deux bugs rapportés par l'utilisateur, une marche demandée — referment trois trous sans toucher la décision :

1. **Un projet neuf est NU.** Un utilisateur frais ouvrait `/v3/lab` et trouvait un produit déjà peuplé (« paiement », « catalogue ») ; pire, la suggestion « Crée une idée pour mon app » **GREFFAIT** une branche « une idee pour mon app » — « crée » est un verbe fort de GREFFER dans la grammaire fermée (ADR 0057), la phrase n'était pas canonique. Deux causes, deux corrections : **(a)** le twin `lib/v2/composition.ts` exporte **`bareTree()`** — un projet neuf est un arbre **NU** : une seule racine `app`, zéro branche de démo — et `V3Session.tsx` le passe à `turnsOf`/`replayTo` (les twins acceptent l'arbre initial en paramètre ; **le seed de démo reste celui des écrans V2**, qui illustrent les concepts sur un exemple) ; **(b)** une suggestion du lab n'envoie plus jamais une phrase non canonique : la suggestion fautive **PRÉREMPLIT** désormais l'entrée (« capture l'idée : » + focus — l'utilisateur termine SA phrase), les autres envoient des **phrases canoniques prouvées** (« déploie l'application en test », « ouvre l'écran … »). La loi est au miroir des deux côtés : propriétés twin + scénario Playwright « **un projet neuf est NU** ». Le réducteur n'a pas bougé d'une ligne — c'étaient l'assiette (l'arbre initial) et l'entrée (la phrase envoyée) qui mentaient.
2. **LA LOI DE COUVERTURE TOTALE — prouvée sur le VRAI répertoire.** ADR 0059 posait la couverture totale sur des registres déclarés ; **`lib/v3/coverage.test.ts`** la promeut en loi sur le **système de fichiers réel** : le miroir balaie `front/web/app/` et prouve **∀ écran V1 réel + ∀ page ET concept V2 + ∀ lentille V3 → « ouvre l'écran \<slug\> » résout dans le chat** (vers SA route) — un écran ajouté demain et non résolu fait **rougir** ce miroir. La loi a payé le jour même : les **concepts `/v2/[slug]`** (le glossaire) manquaient à l'inventaire — trou attrapé par le test, colmaté en ajoutant les routes du glossaire à `initBuilderState` ; et les collisions de noms (auth/app-auth, lab/ai-lab) sont départagées par un **bonus de slug exact** dans `resolveScreen`. Le pendant visible : l'annuaire « **Tous les écrans** » dans Paramètres (`v3-param-screens`, un `<details>` replié) — tout `state.screens` en liens réels, groupés V3/V2/V1 ; et l'écran Parcours accueille le projet nu (état vide amical + CTA vers le lab) au lieu d'un graphe fantôme.
3. **Le menu Code — VS Code LIVE.** La barre V3 passe à **6 entrées** (« Code » avant Paramètres — le compte épinglé par l'e2e) : `/v3/code` rend un **openvscode-server réel** (conteneur `gitpod/openvscode-server` sur l'hôte, route Traefik **`vscode.sagedesk.fr`**, certificat Let's Encrypt), **gaté par connection-token** — l'URL tokenisée vit dans `AIDOS_VSCODE_URL` (`.env.local`, gitignoré ; zéro fuite dans les fichiers suivis), la page est un composant **serveur** qui la lit ; sans configuration, repli honnête (`v3-code-unconfigured` : la lentille `/v2/code` + le lien `vscode://file`). **OpenQuestion** (exception bootstrap, §6) : le **multi-utilisateur** — un seul serveur partagé aujourd'hui ; le par-utilisateur (un conteneur par session, une vraie authentification devant Traefik) est une décision d'infrastructure à part entière.

Les portes : miroirs `lib/v2` + `lib/v3` verts, **vitest 2027/2027** (la loi de couverture incluse), build Next vert (`/v3/code` émise), **Playwright v3 6/6** (dont « un projet neuf est NU »), tsc/biome propres. Les twins de l'ADR gardent leur autorité intacte : la session, le flow, le catalogue n'ont pas changé — seules l'assiette (l'arbre initial), l'entrée (les suggestions canoniques) et la surface (Code) ont bougé.
