# ADR 0057 — L'IA Builder : un chat qui fait tout, par une grammaire d'intentions fermée

- **Statut :** accepté (décision humaine, 2026-06-12)
- **Date :** 2026-06-12
- **Contexte KRD :** §115 (l'idée, candidat-vérité) · §49 (composition fractale) · S22 (la vague de rouge / impact) · ADR 0055 (l'échelle fractale vivante) · ADR 0056 (le graphe de connaissance du code) · ADR 0052 (déploiement gaté) · ADR 0054 (Fable 5, modèle d'agent déclaré) · CLAUDE.md §2 (le mur) · §6/§8 (déterminisme-first) · §9 (anti-overwrite) · WB2-27 (écran `/v2/builder`)

## Contexte

L'utilisateur veut **UN écran, UN chat qui fait TOUT** : capturer un besoin, faire pousser l'arbre, promouvoir une idée, mesurer un impact, lire l'état, déployer — sans naviguer entre dix panneaux. Le risque évident est le **chat-magie** : un prompt géant devant un LLM qui « comprend » le message, décide seul de l'action, et exécute — non déterministe, non testable, non auditables ses refus, et une porte ouverte dans le mur (un modèle qui « comprend » finit par écrire). Le déterminisme-first (§6/§8) interdit exactement cela : ce qui peut être une fonction pure DOIT être du code, et le LLM n'est que l'exception gatée. La question n'était donc pas « comment brancher un LLM sur le Workbench » mais : **quelle forme déterministe donner à un chat total ?**

## Décision

1. **La grammaire d'intentions est FERMÉE et DÉCLARÉE** : `INTENT_KINDS = {capturer_idee, greffer, promouvoir, impacter, interroger, deployer}` (twin pur `front/web/lib/v2/builder.ts`). Le chat ne sait faire que ce qui est déclaré — jamais « un peu de tout ». Un jeu clos, au-dessus de la ligne, comme tout vocabulaire KRD.
2. **`classifyIntent` est un ALGORITHME lexical déclaré, jamais un prompt** : tokens pliés (accents NFD, ≥ 3 chars), lexiques déclarés par intention (verbes forts +2, indices faibles +1), tri score ↓ puis ordre déclaré (stable). Total, pur, déterministe — les poids sont **déclarés, jamais appris** (§8). Le classement complet EST « **les types de réponse possibles** ».
3. **`understand` expose le verdict, jamais une devinette** : « **l'attente** » = le candidat net en tête (`comprise`) ; une **égalité en tête est une AMBIGUÏTÉ détectée et remontée** (`ambigue`) — l'écran OFFRE les candidats (chips cliquables), le choix n'est **jamais tranché en silence** ; aucune accroche = `incomprise` (jamais une invention). Le verdict, les candidats et l'attente sont des **données rendues visibles** à chaque tour.
4. **`applyIntent` est un RÉDUCTEUR PUR event-sourcé** : même `(état, message)` → même `(état', événements, impacts)` ; le journal est **append-only** (§9). « **La réponse** » = les **événements typés du jeu clos** (`idee_capturee · arbre_greffe · kernel_propose · impact_calcule · etat_lu · deploiement_propose · refus`) — jamais de la prose libre ; « **les impacts** » = la **vague calculée** (sous-arbre `composes`, idées, kernels), jamais estimée. Une intention ambiguë/incomprise produit un événement `refus` explicable.
5. **Le builder COMPOSE les twins existants, il ne les redonde pas** : l'arbre vivant (`composition` : seed, greffe `growComposes`, placement `placeIntent`, position `positionOf`), l'idée (`composeIdea` — le niveau, la facette et l'échelle sont **pris du nœud d'attache** : le système identifie la coordonnée entière), la promotion (`goal` : `promoteIdea` → kernel proposé, ChangeSet DRAFT), l'impact code (`code-graph`, composé côté écran). Pas de fork, pas de double lexique (ADR 0007 appliqué aux twins).
6. **Le LLM est l'EXCEPTION GATÉE de désambiguïsation** : sur un message ambigu, l'écran peut demander à Claude (CLI `claude --model claude-fable-5`, le précédent `/ai-lab`, ADR 0054) de **reformuler** le message en UNE phrase d'intention claire — et cette phrase **repasse par le MÊME pipeline déterministe** (`understand`/`applyIntent`) : le code re-juge, **le code a l'autorité**, le modèle propose et ne décide jamais ; toute panne → `null`, repli sur les chips déterministes.
7. **Le mur est une propriété ∀** : pour TOUTE suite de messages, **aucune intention ne produit une écriture-vérité** — toute idée reste `hasMirror=false`, tout kernel proposé reste `wroteKernel=false` (ChangeSet DRAFT), tout déploiement est **proposé** (gaté ADR 0052), jamais exécuté. Épinglé par une propriété fast-check du miroir `lib/v2/builder.test.ts` (14 tests verts), pas par une intention.

## Conséquences

- **Étendre le chat = déclarer, jamais espérer** : une nouvelle capacité, c'est **une intention ajoutée au jeu clos + son lexique déclaré + sa réduction pure + ses tests** — jamais « le modèle improvisera ». Le coût d'extension est explicite, et chaque extension est prouvée avant d'exister (Mandat A).
- **L'écran `/v2/builder`** (WB2-27) rend le tour ultra-explicite — l'attente, les types de réponse possibles, la réponse (événements), les impacts (la vague) toujours visibles ; enregistré dans `lib/v2/screens.ts` (cohérence WB2-25). La désambiguïsation manuelle (cliquer un candidat) **compose un texte désambiguïsé** qui repasse par le même pipeline — l'écran n'a aucun pouvoir que le twin n'a pas.
- **Le refus est un événement**, pas un silence : l'ambiguïté et l'incompréhension sont des données du journal, auditables — la même honnêteté que les `BlockReason` du mur.
- **OpenQuestions** (exception bootstrap, §6) : **brancher le chat sur le store Postgres réel** (S31/S33 — aujourd'hui l'état est l'arbre seed + l'event-sourcing d'écran) ; **fusionner `/ai-lab` dans `/v2/builder`** à terme (un seul point d'entrée conversationnel, le lab devenant un mode du builder) ; un intent **`ancrer_code` dédié** (l'ancrage requirement→code d'ADR 0056 mérite sa propre entrée du jeu clos plutôt qu'un cas d'`impacter`).
