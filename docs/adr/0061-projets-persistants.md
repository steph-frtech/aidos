# ADR 0061 — Les projets persistants : un projet = un transcript nommé, rouvrir = rejouer

- **Statut :** accepté (décision humaine, 2026-06-12)
- **Date :** 2026-06-12
- **Contexte KRD :** ADR 0060 (Workbench V3 — une session, cinq lentilles ; l'OpenQuestion « la persistance du transcript par projet ») · ADR 0057 (l'IA Builder event-sourcé — le réducteur pur, la grammaire fermée) · ADR 0058 (le cycle de vie dans le chat) · CLAUDE.md §2 (le mur) · §6/§8 (déterminisme-first, « done » calculé) · §9 (anti-overwrite, append-only) · S55 (l'isolation par projet, RLS)

## Contexte

La V3 a livré la session rejouable (ADR 0060) : UN transcript, cinq lentilles, l'état **jamais stocké, toujours rejoué** (`replayTo` = le fold du réducteur `applyIntent`). Mais cette session était **éphémère** — le transcript vivait dans un `useState` du provider : fermer l'onglet, recharger la page ou changer de machine effaçait tout. L'ADR 0060 l'avait nommé en OpenQuestion (« la persistance du transcript par projet ») ; le mandat utilisateur l'a exigé en clair : *« Quand je crée une app ça doit créer un projet que je peux rouvrir avec tout l'historique partout le chat tout partout même état. »* Le danger, en le construisant, est connu : persister **l'état** (le snapshot d'écran) au lieu de la **vérité** (le transcript) — et inventer une couche de synchronisation entre les deux, c'est-à-dire réintroduire la divergence que l'event-sourcing avait rendue structurellement impossible. La question : **comment rendre la session durable sans jamais stocker un état ?**

## Décision

1. **Un PROJET = un TRANSCRIPT NOMMÉ PERSISTÉ — l'état n'est JAMAIS stocké, il est REJOUÉ.** Le `ProjectRecord` ne contient que l'identité (`id`, `name`), **LE transcript** (la seule vérité), les réponses IA (une décoration, décision 6) et `savedAt`. ROUVRIR un projet = `parseProject` puis **rejouer** (`turnsOf`/`replayTo`, déjà prouvés déterministes par le miroir d'ADR 0060) : « **le même état partout** » est une **CONSÉQUENCE du rejeu déterministe prouvé, pas une synchronisation** — aucun snapshot, aucun cache d'état, aucun protocole de réconciliation n'existe, donc aucun ne peut diverger.
2. **Le twin pur `front/web/lib/v3/project.ts` — 5 propriétés au miroir** (`lib/v3/project.test.ts`, 5/5 verts, Vitest + fast-check) : **l'aller-retour sans perte ∀** (`parseProject(serializeProject(p)) ≡ p` — le transcript, les réponses, tout) ; **rouvrir = rejouer le même état** (la composition avec `replayTo` ∀ projet) ; **le parse TOTAL & FAIL-CLOSED** (du bruit, un champ manquant, un transcript non-textuel → `null` — jamais une invention, jamais une exception) ; **le slug stable** (`projectSlug` : accents pliés, ascii, borné à 48, non vide pour un nom non vide) ; **le tri déterministe** (`sortProjects` : `savedAt` décroissant, départage stable par `id`). PAS d'horloge dans le twin : `savedAt` est **FOURNI** par la couche impure, jamais lu ici.
3. **Le magasin = des fichiers JSON côté serveur** (`.aidos-projects/` à la racine du dépôt, **gitignoré**) via les server actions `app/v3/projects-actions.ts` (`listProjectsAction`, `loadProjectAction`, `saveProjectAction`, `createProjectAction`, `setActiveProjectAction`). La couche impure ne fait QUE l'E/S : la sérialisation, le parse fail-closed, le slug et le tri restent dans le twin ; un id hostile est refusé par motif (`/^[a-z0-9-]{1,64}$/`, fail-closed) ; un fichier bruité est **ignoré**, jamais réparé. **`Date.now()` vit UNIQUEMENT ici** (le `savedAt` posé à la sauvegarde) — la seule lecture d'horloge de toute la persistance V3. Esprit append-only (§9) : on ajoute, on resauve, on ne détruit jamais.
4. **Le cookie de projet actif** (`aidos-v3-project`) : le layout serveur `/v3` le lit à chaque rendu, **charge** le record (fail-closed) et l'injecte dans la provider — **clée par l'id du projet** : basculer de projet remonte la session, le rejeu repart du bon transcript (la bascule sauve l'en-cours via `persistNow` avant de poser le cookie). Sans cookie : le plus récemment sauvé. Chaque `send` et chaque `rewindTo` déclenche une sauvegarde **débouncée** (800 ms) — l'utilisateur ne « sauvegarde » jamais à la main.
5. **L'auto-création « Mon application » au premier passage** : sans AUCUN projet, le layout en crée un (`createProjectAction("Mon application")`, transcript **vide** — le projet nu d'ADR 0060 addendum 2) — **créer une app CRÉE un projet**, l'utilisateur atterrit TOUJOURS dans un projet persisté, sans formulaire ni étape. La nav V3 porte le commutateur (`v3-project-name`, `v3-project-panel`, `v3-project-item`, `v3-project-new-name`, `v3-project-create`) : lister, basculer, créer — en français simple.
6. **Les réponses IA persistées en DÉCORATION** : les `replies` (les phrases conversationnelles de Claude, par index de tour) sont rangées avec le projet pour que la conversation rouvre **telle quelle** — mais **la vérité reste le transcript** : un projet se rejoue intégralement sans elles (le rejeu ne lit que les messages), et un record sans la moindre réponse est un projet valide. Perdre le décor ne perd rien de l'état.

## Conséquences

- **Le mur est inchangé** : un projet est un transcript de **propositions** ; le sauver, le rouvrir, le rejouer ne produit aucune écriture-vérité (la loi ∀ du réducteur — test 14, ADR 0057 — couvre chaque pas du rejeu, persisté ou non). Le magasin n'écrit que `.aidos-projects/`, jamais kernel/mirrors/fitness.
- **La persistance n'a coûté aucun moteur** : pas d'undo-manager, pas de couche de sync, pas de migration d'état — un twin de 4 fonctions pures + une couche d'E/S de 5 actions. C'est le dividende attendu de l'event-sourcing (ADR 0060) : quand la vérité est le transcript, « durable » = écrire un fichier.
- **Les e2e restent hermétiques** : l'IA coupée, un projet se crée, se nourrit, se rouvre — le scénario Playwright prouve le cycle sans modèle ni réseau.
- **OpenQuestions** (exception bootstrap, §6) : **migrer le magasin vers le schéma Postgres `projects`** (S55 — l'isolation RLS par projet ; les fichiers JSON sont la marche bootstrap, le twin `serializeProject`/`parseProject` est déjà le format d'échange) ; **le renommage et l'archivage** des projets (aujourd'hui : créer et basculer — renommer/archiver sont des décisions de cycle de vie à grailler) ; **le partage multi-utilisateur** (un magasin par déploiement aujourd'hui ; partager un projet = partager un transcript — rejouable à l'identique par construction — mais l'identité, les droits et la concurrence sont une décision à part entière).
