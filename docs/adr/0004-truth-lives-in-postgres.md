# All KRD truth and its meta live in Postgres, append-only and content-addressed, never in scattered files

The "kernel" of AIDOS is **not** a folder of files: it is a set of **Postgres schemas**. All KRD truth and its meta — `kernel` (DSL ASTs: entities, policies, operations, controls, actions, expr + invariants + budgets), `mirrors` (mirror records + their source: Gherkin text, property specs, fixture data), `ideas` (candidate-truths + provenance), `changesets` (transactional history `DRAFT / APPLIED / REVERTED`), `dag` (stable phases + changeset edges), `brain` (`MemoryItem` + embeddings via **pgvector**), `context` (the derived ContextGraph + `ContextGraphDecision`), `provenance` ("who wanted what, when, why"), and `fitness` (NIVEAU 3 grammar + waterline + the definition of "passed", read-only) — lives in the base. The base is **append-only** (nothing destroyed; the head is mutable but every prior version is retained) and **content-addressed** (version = hash of content). We chose this because truth needs one authoritative, queryable, transactional home with first-class history — and Postgres already is one. The agent owns implementation (code, projections); the human owns truth (the base); the harness enforces the wall between them.

Code in the repo (Go, `.feature` files, Next components) is **projection** — a regenerable mirror implementation, not the truth. Canonical `.feature` files are stored in the base and **materialized to disk** for the runner (Godog, Playwright); the disk copy is **derived**, the base is **authoritative**. Regenerating the materialized files from the base must be idempotent; a disk `.feature` that drifts from the base is stale, not a source.

## Considered Options

- **Truth as files in git (the Tome arborescence taken literally — `/kernel/spec`, `/mirror/*.feature`, idea files).** Rejected. Git gives history and branches but no transactional integrity across many related records, no query (you cannot ask "every mirror reflecting kernel entity X" without a grep that does not understand the AST), no enforced content-addressing, and no row-level permission boundary. The wall would have to be reimplemented as path rules on top of a filesystem that has no notion of truth. Files also invite silent hand-edits — exactly the monster CLAUDE.md §9 forbids. Files remain the home of *projections* (code, materialized `.feature`), never of truth.
- **Dolt (a git-for-data SQL database) as the versioned truth-store.** Seriously considered: Dolt natively unifies "SQL database" with "git-style versioning, branches, merges, diffs" — which is most of what the `changesets`/`dag` schemas need. Rejected: it adds a second database engine alongside the Postgres the rest of the stack already mandates (sqlc, pgx, Atlas, Testcontainers, pgvector, telemetry sink), splitting truth from the operational base and doubling the operational surface. Postgres **absorbs Dolt's versioning role** through append-only history tables, content-addressed versions, and the explicit `changesets` + `dag` schemas — so the versioning value is kept without the second engine. **Dolt is abandoned** (CLAUDE.md §3, frozen stack).
- **Postgres as the single truth-store (chosen).** One engine for truth *and* operations: JSONB for the DSL ASTs, history tables + version=hash for append-only content-addressing, `changesets`/`dag` for the version DAG, **pgvector** in `brain` for embeddings. Transactions make a ChangeSet that mutates `kernel` spec and `mirrors` proof atomic (the bicephalous co-versioning of ADR 0002). Row/schema GRANTs give the wall a real, database-enforced boundary. It is the same Postgres the frozen stack already standardizes on, so no new engine enters the system.

## Consequences

- **The wall is enforced twice (defense in depth).** (1) A `PreToolUse` Go hook refuses any agent write into the truth zones and returns an actionable `BlockReason` (`code, severity, explanation, how_to_fix[]`). (2) Postgres **GRANTs**: the agent's DB role has **no** write GRANT on the truth tables. Only the `aidos` CLI — via an **approved changeset**, under a dedicated DB role — writes truth. Either layer alone would suffice; both together mean a hook bug cannot grant database write, and a missing GRANT still produces a clear hook message.
- **The agent's only door to the kernel is `idea → mirror → /goal → human approval`.** The agent never writes truth in passing. To change a truth it creates an **idea**, writes the **mirror** (which is red — that red *is* the goal), and opens a **`/goal`** for human approval; the approved changeset is what the CLI applies. There is no other path through the wall.
- **Everything is a recorded decision, never a silent edit.** An override is a changeset + ADR + provenance, not a mutation; nothing is destroyed (append-only), so any head is reconstructible and any change is auditable to "who wanted what, when, why".
- **Materialization is one-directional.** The base → disk `.feature` projection is regenerable and must be treated as a cache; editing the disk copy to change a behaviour is forbidden (it is a mirror change, which must go through a SemanticDiff + changeset). Runners read disk; authors read/write the base.
- **Hard to reverse.** sqlc/pgx typing, Atlas expand-contract migrations, the GRANT model, the `changesets`/`dag` engine, and pgvector in `brain` all assume one Postgres truth-store. Moving truth into files or a second engine later would mean rebuilding the wall's GRANT layer, the co-versioning transaction envelope, the content-addressing, and the embedding index at once.
- **The deliberate no:** git/jj still version *code* branches, and Atlas still manages *schema* migrations — but neither is the home of truth. Git holds projections; Postgres holds the truth those projections reflect.

## Addendum — 2026-05-30: Doltgres re-evaluated and re-rejected for the truth-store; Dolt moves to the emitted-app datastore

The original "Considered Options" weighed **Dolt** but never evaluated **Doltgres** (Dolt speaking the Postgres wire protocol), which would have dissolved the "second/different engine" objection. We ran a sourced May-2026 recheck (adversarially judged). Verdict: **keep Postgres as the single truth-store** — confidence high. Doltgres does **not** clear the bar:

- **Beta, no GA.** ~13 months in beta; the ~April-2026 1.0 target slipped; current line v0.56.4 (2026-05-28). Not a Postgres fork — a Go reimplementation on prolly trees emulating the Postgres wire.
- **No working pgvector.** Only partial `CREATE EXTENSION` parsing; Dolt 2.0's native `VECTOR` is MySQL-flavored, incompatible with pgvector operators / `ivfflat`/`hnsw` DDL. The `brain` schema (S31, pgvector HNSW recall) cannot be hosted — and even a hybrid keeps pgvector on real Postgres, so a second engine buys `brain` nothing.
- **Not safe for a concurrent changeset engine.** Query parser not thread-safe under concurrent pgx connections (issue #2581); missing serializable primitives `pg_advisory_xact_lock` / `FOR UPDATE SKIP LOCKED` / `LOCK TABLE` (issue #2600).
- **Atlas/sqlc unverified** against its still-incomplete `pg_catalog` (~5.2× slower than Postgres).

**Two corrections to the body above, recorded honestly:** (1) the implicit "Dolt is slow" reasoning is now **false** — Dolt 2.0 (2026-05-11) is ~8% faster than MySQL; the real blocker is that Dolt is **MySQL-wire** and would shatter the Postgres-native frozen stack. (2) Dolt's structured 3-way merge is *good*, but **orthogonal** to KRD's `MergeSemantic` (S25 = merge the cut, re-run **all** mirrors, red blocks) — so it buys less than it appears; KRD's merge is application logic over any store. The load-bearing concept the Tome mandates is **content-addressing (version = hash)**, delivered by S01/S24 on Postgres at **per-Layer** granularity (vs Dolt's commit granularity, which mismatches the per-Layer red wave S22).

**The split that resolves it (confirmed 2026-05-30, ADR 0006):** the AIDOS **truth-store stays Postgres**; **Doltgres** (Dolt's Postgres-wire build) becomes the **data-versioning target for the apps AIDOS *emits*** — the "BDD du résultat codé" — keeping one Postgres dialect across the whole system. That is exactly the re-open trigger this ADR anticipated ("a need to version large operational datasets with cheap data-scale branching"): it lives in the *built product's* datastore, not the OS truth-store. The emitted-app store **knowingly accepts Doltgres's beta status** (replaceable slot, plain-Postgres fallback, spike-validated); the **truth-store does not** — the blockers above keep it on Postgres.

**Re-open trigger (for the truth-store only):** Doltgres reaches 1.0/GA **and** ships pgvector-compatible vectors **and** closes #2581 + #2600. Until then, the truth-store is Postgres.

**Honesty caveat:** this recheck's evidence base leaned toward "keep Postgres"; the cheapest adversarial check is **one recorded spike behind the wall** (Doltgres in a Testcontainer; pgx + sqlc + Atlas against `dag`/`changesets`; attempt the `brain` schema) to convert the low-confidence Atlas/sqlc claims into evidence. Evidence-gathering, not a pilot.
