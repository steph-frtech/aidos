# ADR 0062 — L'instance, les workspaces et la grille : les 7 mandats (envs dev → staging → prod, palette ⌘K, VS Code par environnement, config d'instance, lentille Instance, vue Spécifications)

- **Statut :** accepté (décision humaine, 2026-06-12)
- **Date :** 2026-06-12
- **Contexte KRD :** ADR 0059 (l'échelle d'environnements — le cliquet généralisé sur `ENV_LADDER`, une donnée) · ADR 0060 (Workbench V3 — une session, des lentilles ; la loi de couverture totale, addendum 2) · ADR 0061 (les projets persistants — rouvrir = rejouer, le magasin `.aidos-projects/`) · ADR 0057 (le réducteur pur, la grammaire fermée) · CLAUDE.md §2 (le mur) · §6/§8 (déterminisme-first, « done » calculé) · §9 (anti-overwrite, append-only) · §23 (la verticale — niveaux × facettes)

## Contexte

La V3 avait la session rejouable (ADR 0060) et les projets persistants (ADR 0061) — mais sept frictions restaient, toutes remontées par l'usage réel : l'échelle disait « test » là où l'utilisateur dit **dev** ; un barreau déployé ne se **voyait** pas (la carte montrait une version, jamais l'app) ; ~160 écrans existaient sans **un seul endroit** pour les atteindre ; le VS Code live (addendum 2 d'ADR 0060) ouvrait le dépôt AIDOS, jamais **le projet de l'utilisateur** ; les URLs de l'instance (workbench, Postgres, Traefik, docs…) vivaient en dur dans les écrans ; rien ne disait si ces outils étaient **vivants** ; et les vérités du projet (idées, kernels) n'avaient pas de vue d'ensemble — ni leur **statut de cycle de vie**, ni leur place sur la **grille** niveau × facette, ni les **impacts** du dernier tour de chat. Sept mandats, une décision.

## Décision

1. **L'échelle est renommée `dev → staging → prod` — le vocabulaire de l'utilisateur, et c'est une DONNÉE.** `ENV_LADDER = ["dev", "staging", "prod"]` (`lib/v2/builder.ts`) : `envs.test` n'existe plus, la phrase canonique devient « **déploie l'application en dev** » (puis staging, puis prod). Parce que l'échelle est une donnée déclarée (ADR 0059) et que les libellés par barreau sont des `Record<EnvName, …>` plutôt que des cas codés, le renommage n'a coûté que des mots — **le cliquet d'échelle est inchangé** : chaque barreau, dans l'ordre, toujours (déployer en staging exige la version passée en dev ; un saut est refusé avec son explication).
2. **« Voir le résultat » par environnement — la préview reconstruite des kernelVersions EMBARQUÉES.** Sur `/v3/environnements`, chaque barreau déployé porte « Voir le résultat » (`v3-env-view-<env>`) : la préview (`v3-env-preview`) rend **l'app telle que déployée LÀ** — `projectionAt` filtre l'état sur les `Deployment.kernelVersions` du barreau puis **réutilise `emitApp`** (le même émetteur déterministe, jamais un second chemin) ; jamais les kernels courants. Pure : même déploiement → même app, même version — et l'écart (la dérive vs les kernels courants) reste calculé à chaque rendu.
3. **La palette ⌘K — le meilleur endroit UX pour ~160 écrans, nourrie par l'inventaire DÉCLARÉ.** ⌘K / Ctrl+K (ou le bouton du pied de nav, l'événement `PALETTE_OPEN_EVENT`) ouvre une modale (`v3-palette`, `v3-palette-input`, `v3-palette-item`) : les 8 lentilles V3 d'abord, puis **tous les écrans atteignables de la session** — `state.screens`, le **même inventaire** que « ouvre l'écran… », celui que la loi de couverture totale (ADR 0060 addendum 2) prouve complet. Le filtrage est un **pli d'accents + `includes`** (un algorithme pur, jamais un prompt — §6), le plafond de résultats est déclaré (12), Entrée ouvre le premier, Échap ferme. La palette **navigue** (`router.push`) — elle n'écrit rien.
4. **VS Code sur LE PROJET, par environnement — l'émetteur `filesOf` écrit le workspace, le conteneur monte le volume.** Le twin pur `lib/v3/emit-files.ts` : `filesOf(projectName, app) → EmittedFile[]` — README.md (nom, version, inventaire), `schema.sql` (une table par entité), `routes.json`, un JSON par entité — **déterministe octet pour octet** (même app → mêmes fichiers), chemins relatifs sûrs, total (une app vide émet un README lisible). La couche impure `emitWorkspaceAction` (`projects-actions.ts`) écrit ces fichiers sous **`.aidos-projects/<id>/workspace/<env>/`** — fail-closed (id hostile, barreau hors `dev|staging|prod`, projection difforme → `{ok:false}`), chaque chemin **confiné** au dossier du workspace (défense en profondeur), écrasement idempotent, jamais de suppression (§9). Le conteneur `aidos-vscode` (openvscode-server) **monte `.aidos-projects` → `/home/workspace/projects`** : `/v3/code` offre un onglet par barreau + l'onglet « AIDOS (le moteur) » ; « Préparer le workspace » (`v3-code-emit` — l'app déployée sur CE barreau, re-projetée des kernelVersions embarquées) puis « Ouvrir dans VS Code » (`v3-code-open`) sur le dossier du projet et de l'environnement.
5. **La config d'instance — un jeu d'outils DÉCLARÉ, un parse fail-closed, un fichier gitignoré — prêt cloud.** Le twin pur `lib/v3/instance.ts` déclare **`INSTANCE_TOOLS`** (7 outils clos : workbench, db, monitoring, traefik, vscode, docs, shop — chacun `key + labelKey + defaultUrl + probe`) : étendre l'instance = déclarer un outil, une donnée. `parseInstanceConfig` est **TOTAL & FAIL-CLOSED** : du bruit → les défauts ; une valeur non-textuelle invalide TOUT (jamais une config moitié-inventée) ; les clés inconnues ignorées, les absentes complétées ; `serializeInstanceConfig` est canonique — l'aller-retour est sans perte ∀. Le fichier **`.aidos-instance.json`** (racine du dépôt) est **gitignoré** : la config décrit VOTRE instance — locale aujourd'hui, cloud demain, le même twin.
6. **La lentille Instance — des sondes RÉELLES + `docker ps`.** `/v3/instance` (`v3-instance`) : une tuile par outil déclaré (`v3-inst-tool`) avec son statut sondé — `probeInstanceAction` sonde en parallèle (HEAD puis GET, 3 s max, **toute réponse HTTP = VIVANT**, le 403 du connection-token compris) sur une table d'URLs **déclarée** (les domaines publics ne se résolvant pas en local, jamais devinée) ; `dockerPsAction` liste les conteneurs **connus** (`docker ps --format json`, motif déclaré, fail-closed → `[]`) dans `v3-inst-docker`. La config s'édite et se sauve (`v3-inst-config`, `v3-inst-save`, `v3-inst-saved`) — l'entrée **repasse par le parse total du twin** avant d'être écrite.
7. **La vue Spécifications — le statut CALCULÉ, la grille aux comptes conservés, les impacts SURLIGNÉS.** Le twin pur `lib/v3/specs.ts` : `specsOf(state) → SpecRow[]` — une ligne par vérité du projet, le statut **calculé, jamais déclaré** : `idee` → `kernel` → **l'env LE PLUS HAUT qui embarque sa version** ; `gridOf(rows) → GridCell[]` — la projection niveau × facette aux **comptes conservés** (Σ cellules = specs : jamais une perte, jamais une invention), ordre stable. `/v3/specs` rend LA GRILLE en haut (7 niveaux `SOURCE_ORDER` × 8 facettes — chaque case compte) et la liste en bas (badge de statut amical, intention, coordonnée, **scénario replié** par spec — `v3-specs-scenario`). « Quand le chat propose un changement, je VOIS les impacts » : les cases touchées par le **dernier tour** (`turns[dernier].impacts`, mappés vers leur SpecRow) s'allument en ambre (`data-impacted="true"`) ; cliquer une case **filtre** la liste (`v3-specs-cell`, `v3-specs-filter`, `v3-specs-clear`). Lecture seule — tout est projeté du rejeu, rien n'est stocké ici.

## Conséquences

- **Le miroir `lib/v3` : 52/52 verts** (Vitest + fast-check, 8 fichiers) — les 37 d'ADR 0060/0061 (session 6, flow 6, params 20, project 5) + coverage 3 + les trois twins neufs : `emit-files.test.ts` **5** (reproductible octet pour octet, chemins uniques/relatifs/sans traversée, README versionné + schéma par entité, totalité sur app vide et noms arbitraires ∀), `specs.test.ts` **4** (statut qui suit le cycle idee → kernel → l'env le plus haut, déterminisme, **Σ cellules = specs**, les cellules impactées d'un tour se retrouvent), `instance.test.ts` **3** (jeu clos à clés uniques, `parse(serialize(c)) ≡ c` ∀, du bruit → les défauts).
- **Le mur est inchangé** : tout est lecture ou projection ; les seules écritures sont des **fichiers d'app émise** (le workspace — la même nature que `back/gen/`) et `.aidos-instance.json` (la description de VOTRE instance) — jamais kernel/mirrors/fitness. La palette navigue, la grille projette, la préview recalcule.
- **Le renommage a prouvé que l'échelle est une donnée** : `dev → staging → prod` n'a touché que des libellés, des phrases et des clés — le cliquet, le réducteur et ses lois ∀ n'ont pas bougé d'une ligne. Le vocabulaire de l'utilisateur est entré dans le produit sans coût structurel — c'est exactement ce que « l'échelle est une DONNÉE » (ADR 0059) promettait.
- **La nav V3 passe à 8 lentilles** (lab, parcours, **specs**, history, environnements, code, **instance**, paramétrage — `toHaveCount(8)` épinglé par l'e2e) ; les e2e restent **hermétiques** (IA coupée, « déploie l'application en dev » dans le jeu prouvé).
- **OpenQuestions** (exception bootstrap, §6) : **les déploiements réels par environnement** (aujourd'hui un déploiement est un événement du transcript + un workspace de fichiers ; trois stacks réelles dev/staging/prod — conteneurs, routes Traefik, bases — sont une décision d'infrastructure à part entière, ADR 0052) ; **le monitoring réel à brancher** (l'outil est déclaré, sa sonde attend une URL — Grafana/Uptime ? une décision outillage) ; **le partage des workspaces** (un openvscode-server partagé qui monte tous les projets ; le par-utilisateur — un conteneur par session, une authentification devant Traefik — rejoint l'OpenQuestion multi-utilisateur d'ADR 0060/0061).
