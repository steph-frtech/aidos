# ADR 0059 — L'échelle d'environnements et la couverture totale : le cliquet généralisé, le déploiement réel gaté, le delta au grain code, chaque écran atteignable

- **Statut :** accepté (décision humaine, 2026-06-12)
- **Date :** 2026-06-12
- **Contexte KRD :** ADR 0058 (le cycle de vie dans le chat : générer, test→prod, deltas) · ADR 0057 (l'IA Builder, grammaire d'intentions fermée) · ADR 0056 (le graphe de connaissance du code, `anchorSymbols`/`impactOf`) · ADR 0052 (pipeline de déploiement gaté des apps émises, `deployStack` de l'AI Lab) · WB2-25 (le registre des écrans, `lib/v2/screens.ts`) · CLAUDE.md §2 (le mur) · §6/§8 (déterminisme-first, « done » calculé) · §9 (anti-overwrite, append-only) · WB2-27 (écran `/v2/builder`)

## Contexte

L'ADR 0058 a mis le cycle de vie dans le chat — générer, déployer en test puis en prod (le cliquet), voir les deltas — mais il a laissé **quatre bords coupés**, nommés dans ses propres OpenQuestions. (1) Le jeu `{test, prod}` était **codé en deux cas** : ajouter un staging aurait demandé un troisième `case`, alors que la loi du cliquet est la même à chaque barreau. (2) Le déploiement **réel** (docker/Traefik) restait un lien vers `/v2/deploy` — le chat séquençait, mais le geste final vivait ailleurs, sans pont entre l'échelle in-model et le pipeline gaté ADR 0052. (3) Le delta comptait des **kernels**, jamais des **fonctions** : « 2 kernels d'écart » ne dit pas *quelles fonctions exactes* la dérive touche, alors que l'ADR 0056 sait déjà ancrer une coordonnée sur ses symboles de code. (4) Le chat « faisait tout » — sauf **aller quelque part** : aucun moyen d'atteindre les 27 autres écrans du Workbench depuis la conversation, alors que WB2-25 maintient déjà un registre déclaré de tous les écrans. La question n'était donc pas « ajouter des features au chat » mais : **comment fermer ces quatre bords sans ouvrir un seul cas codé — par des données déclarées, des projections pures et des lois prouvées ?**

## Décision

1. **L'ÉCHELLE D'ENVIRONNEMENTS EST UNE DONNÉE DÉCLARÉE, le cliquet est GÉNÉRALISÉ** : `ENV_LADDER = ["test", "staging", "prod"]` (`front/web/lib/v2/builder.ts`) — close, **ordonnée**, et `BuilderState.envs` devient un `Record<EnvName, Deployment | null>` sur cette échelle. La loi est UNE, paramétrée par le barreau : **déployer au barreau i exige que la MÊME version exacte de l'app (`emitApp(state).version`) soit posée au barreau i−1** ; sauter un barreau (prod directe, staging directe, test→prod sans staging) est REFUSÉ avec un événement explicable portant son `env` ; et **toute nouvelle promotion ré-arme CHAQUE barreau supérieur** (la version d'app change → toute l'échelle au-dessus du test re-devient refusée tant que la nouvelle version ne l'a pas regravie, barreau par barreau). Le miroir le prouve **∀ barreau** (propriété, pas trois exemples). Étendre l'échelle = déclarer un barreau dans `ENV_LADDER` (une donnée), jamais coder un cas — exactement la réponse à l'OpenQuestion « environnements multiples » de l'ADR 0058. Les phrases canoniques : « déploie l'application en test | staging | prod » (le barreau est parsé du message ; un seul kind d'événement `deploiement` portant son champ `env` remplace le couple `deploiement_test`/`deploiement_prod`).
2. **Le DÉPLOIEMENT RÉEL entre dans l'écran — GATÉ par l'échelle, approuvé par le CLIC** : l'écran `/v2/builder` porte un bouton « Déploiement réel » (`v2-builder-deploy-real`) qui n'est **armé que lorsque l'échelle in-model est gravie jusqu'au sommet** (`envs.prod !== null`) — le cliquet généralisé est la *condition d'armement*, et **le clic humain EST l'approbation** (le geste, pas un agent). L'action (`deployRealAction`, server action de `app/v2/builder/actions.ts`) **RÉUTILISE le pipeline gaté ADR 0052** : elle appelle `deployStack()` de `/ai-lab` (réémission best-effort `aidosappemit` + `docker compose up -d` sur la stack fixe, URL live Traefik) — **jamais un second chemin de déploiement**. Le mur tient : c'est une action au-dessous de la ligne (émettre + lancer l'app émise), aucune écriture-vérité. **L'émission réelle depuis les kernels in-model reste une OpenQuestion (S45)** : aujourd'hui le pipeline redéploie l'app émise des specs du projet AI Lab ; brancher `emitApp` (les kernels proposés du chat) sur l'émetteur réel est l'étape suivante, pas celle-ci.
3. **Le DELTA descend AU GRAIN CODE — ADR 0058 × ADR 0056** : `codeDeltaFor(kernels, tree, codeNodes, codeEdges) → CodeDelta[]` croise l'**écart d'environnement** (les kernels hors de l'ensemble déployé, ADR 0058) avec l'**ancrage code** (ADR 0056) : pour chaque kernel d'écart, les **fonctions/classes exactes** ancrées sur sa coordonnée (`anchorSymbols`, top-3 `AnchorSuggestion {nodeId, name, file, score}`) et la **taille de la vague de rouge code** (`impactOf` de la meilleure ancre). « 2 kernels d'écart » devient « *ces fonctions-là*, et une vague de N symboles » — compté, jamais estimé. PURE & TOTALE & DÉTERMINISTE : un graphe de code vide → des ancres vides, jamais une erreur. L'écran le rend dans le panneau environnements (`v2-builder-code-delta`, ancres cliquables vers `/v2/code`).
4. **La COUVERTURE TOTALE — chaque écran du Workbench atteignable depuis le chat** : une **9ᵉ intention** `ouvrir` (« ouvre l'écran code », « navigue vers le goal ») et `resolveScreen(screens, text) → ScreenRef | null` — un score lexical contre l'**inventaire DÉCLARÉ** : le registre V2 (`SCREENS`, WB2-25) est TOUJOURS couvert par `initBuilderState`, et les écrans V1 s'**injectent en données** (`extraScreens`, le scan serveur — l'inventaire est une donnée, jamais du code). +3 par token du slug de route, +1 par token de libellé, départage stable par route ; **aucune accroche → null** (fail-closed, jamais une route inventée — le refus est un événement). Un écran résolu produit `ecran_ouvert` (ref = la route) ; l'écran le rend en **puce de navigation** (`v2-builder-open-screen`). **LA LOI DE COUVERTURE est au miroir** : ∀ écran du registre V2, « ouvre \<titre\> » résout vers SA route — une propriété sur tout le registre, pas un échantillon.
5. **La règle déclarée « L'IMPÉRATIF DE NAVIGATION COMMANDE »** : un message dont le **premier token** est `ouvre`/`ouvrir`/`navigue` est TOUJOURS l'intention `ouvrir`, avant tout score. **Pourquoi** : `ouvrir` est le seul intent dont la charge utile **CITE naturellement le vocabulaire des autres intentions** — les titres d'écrans contiennent « idée », « goal », « déployer », « impacts »… — donc « ouvre l'écran goal » accrocherait `promouvoir` à égalité et la loi de couverture serait **fausse** sans cette règle. Elle est déclarée dans le code (`understand`), déterministe, et épinglée au miroir — jamais un arbitrage silencieux du modèle.

## Conséquences

- **Le miroir passe de 22 à 29 propriétés** (`lib/v2/builder.test.ts`, verts) : l'échelle déclarée close et ordonnée ; **∀ barreau > 1, sauter un barreau est REFUSÉ** ; le chemin légal test → staging → prod (la même version monte chaque barreau) ; **le cliquet re-mord sur TOUTE l'échelle** (une promotion invalide chaque barreau supérieur) ; **la LOI DE COUVERTURE** (∀ écran du registre V2, « ouvre \<titre\> » résout vers SA route) ; les écrans V1 injectés atteignables (l'inventaire est une donnée) ; `resolveScreen` total, déterministe, fail-closed ; ouvrir un écran introuvable → refus ; `codeDeltaFor` ancre chaque kernel d'écart sur ses fonctions + sa vague, total et déterministe — et le MUR ∀ re-prouvé sur la grammaire à **9 intentions**.
- **Le jeu clos passe à 9 intentions** (`INTENT_KINDS` + `ouvrir`) et le jeu des événements se simplifie en se généralisant : UN kind `deploiement` (avec son champ `env`) remplace `deploiement_test`/`deploiement_prod` ; nouveau kind `ecran_ouvert`. Étendre = déclarer, toujours.
- **Le geste final du cycle de vie est dans l'écran, et il reste gaté trois fois** : par l'échelle in-model (le bouton ne s'arme qu'au sommet), par le clic humain (l'approbation est un geste, pas un agent), et par le pipeline ADR 0052 réutilisé (jamais un second chemin docker).
- **OpenQuestions** (exception bootstrap, §6) : **des labels V1 enrichis** — le scan V1 n'injecte aujourd'hui que des routes/segments ; un **registre V1 déclaré** (titres FR/EN comme `SCREENS`) rendrait la résolution lexicale aussi riche qu'en V2 ; **l'émission réelle in-model → docker (S45)** — brancher `emitApp` (les kernels proposés du chat) sur l'émetteur réel pour que le bouton déploie l'app NÉE de la conversation, pas seulement la stack fixe de l'AI Lab ; **des environnements par projet** — `ENV_LADDER` est globale aujourd'hui ; la déclarer par projet (une donnée par produit) quand le multi-projet arrivera.
